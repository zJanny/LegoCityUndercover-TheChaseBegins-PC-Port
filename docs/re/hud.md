- Layouts (all `.bxaml`, dump with `parseLayout`): `sprites/ui_hud/blend/main.bxaml` (400x240 page), `ui_hearts_control.bxaml` (one per heart; two variants exist, the code loads `sprites/ui_hud/blend/images/ui_hearts_control`), `ui_bosshearts.bxaml` (boss bar, flag 0x10 only). Main holds `UI_HUD` at (3, 0) with `UI_HUD_3DS` (images `UI_HUD_Image_3DS` and `UI_portrait`, both 64x64 at (0, 0) of it), `Stud_Count` (72, -21) with the text element `Studs_Count` (256x13, font size 12, alignment 1), `CombatStud_Count`, `UI_Hearts` (75, 33) with `UI_Hearts_1_3DS` .. `_6_3DS` (16x16 at x = -2, 15, 32, 49, 66, 83, y = -12), `UI_Stud`, the references `userControl` (UI_BossHearts at 334, 0) and `UI_Strike` (UI_StrikeControl, no file), `Struggle_Button`, `UI_Trophy`. Storyboards: `TransitionOn` (1.1 s: HUD and hearts fade in one after the other, hearts 2..6 also slide 9..12.5 px), `TransitionOff`, `Studs_ON` / `Studs_OFF` (0.5 s: `Stud_Count` translate y 0 <-> 53 and opacity), `CombatStuds_*`, `Struggle*`.
- Page init 0x2cedb8 (ev_116affab…) takes a flag word (`DAT_003757a4`, 0xfffdffff at the gameplay start). Flag 0x20 creates the page `Sprites/UI_Hud/Blend/Main` at 0x5186c8; 0x4 creates the stud bars (`FUN_0015b2f0(&0x519760, "Studs")` and `(&0x5197c8, "CombatStuds")`, the latter the combat counter); 0x10 the boss hearts page; 0x400 calls 0x17bb14 (hearts, ev_db0c0947…); 0x2 loads `Fonts/FrontendFont` into 0x3757a0 and registers the draw callbacks of the overlays with `FUN_0023cb90(fadeIn, fadeOut, list, object, callback, 6)`.
- 0x17bb14 loads the eight `heartsBG_*` images (cop, robber, miner, astro, farmer, fire, builder, generic), the elements `UI_HUD_Image_3DS` (0x519238) and `UI_portrait` (0x51923c), `UI_Heart_3DS.png` and `UI_HeartVehicle_3DS.png`, creates six instances of `Sprites/UI_Hud/Blend/Images/UI_Hearts_Control` (0x54 bytes each from 0x519258; storyboards `Loop_Heart`, `Lose_Heart`, `Gain_Heart` and the image `UI_Heart_Image_3DS` of each) and attaches instance i as the child of the main page's element `UI_Hearts_%u_3DS` (i + 1). It sets the heart count `0x519450` = 6 and ends with `0x24581c(page, 0, 0, 1)`; the page is switched on by 0x17c0f4 (`0x24581c(page, 1, 0, 1)` for the page and the six heart instances), which is where TransitionOn runs. The trigger of 0x17c0f4 was not traced.

### Portrait
- Draw callback 0x193604 (ev_26a4818e…; called per frame, draws the page with `FUN_0021d384(alpha, 0x5186c8)`, alpha = `FUN_00235e2c()` * `DAT_00375728` = 1.0): `UI_HUD_Image_3DS` gets `heartsBG_<class>` chosen with the character record's flag tests `FUN_0023a70c(*(player + 0x7c), 0x19..0x1f)` (0x19 cop, 0x1a robber, 0x1b miner, 0x1c astro, 0x1d farmer, 0x1e fire, 0x1f generic, else builder); `UI_portrait` gets the texture of the player slot, loaded by 0x262320 (ev_bb2ff78c…) from `sprites/portraits/<name>.png` where `<name>` is the first word of the `tablescharacters` row (0x372e10 + 0x28 * index); the row index of player 1 is the byte at 0x51b24c: 9 at the gameplay start, row 9 is "police". The composition heartsBG_cop + `sprites/portraits/police.bpng` equals the oracle's portrait (position exact, mean abs 6.7 over the opaque pixels, mostly the soft hexagon edge).

### Hearts
- The count shown is set by 0x2316b4 `SetHearts(n)` (ev_497f0342…; 15 callers, e.g. the character setup 0x17041c and 0x19d3b0 which copies the class byte). Per heart i (0..5): the image is `UI_Heart_3DS` (`UI_HeartVehicle_3DS` while `*(player + 0x7c) + 0x6e` is 0x11a or 0x11c); if `old <= i < n` (gain) it stops `Loop_Heart`, resets `Lose_Heart` and plays `Gain_Heart` once; if `n <= i < old` (loss) it stops the loop, resets `Gain_Heart` and plays `Lose_Heart` once; the count is stored limited to 6 at 0x519450 (read: 4 at the gameplay start).
- 0x193604 per frame: for heart i, if `i == count - 1` and the Loop, Gain and Lose storyboards are all finished (state 6), `Loop_Heart` is started looping (`0x245b40(1.0, 0, sb, 1, 0, 0xffff)`); if `i < count - 1` and its Loop runs (state 1) it is stopped. So only the last heart pulses (scale 1.0, 1.2, 1.0, 1.2, 1.0 within 0.9 s). Lose_Heart ends with the heart at opacity 0.
- Full health: 0x236e28..0x236e54 stores the class attribute "Health" (default argument 4, `r2 = 4` at 0x236e30) at `(controller + 0xe0) + 0x128`, plus 1 when the player has unlock 17 (0x2369a8(17), 0x236e6c); 0x19d3b0 copies that byte to the health u16 at controller + 0x70 and calls `SetHearts`. No class file has a "Health" key (grep over the whole archive), so Chase has the default 4. Oracle at the gameplay start: `0x08552800` (controller + 0x70) = 4, 0x519450 = 4, four hearts on screen.

### Stud bar (counter and icon)
- Object layout (0x519760 for "Studs", 0x5197c8 for "CombatStuds"; init 0x15b2f0, ev_90d85a7d…): +0x0c layout node, +0x10 state (0 hidden, 1 turning on, 2 shown, 3 turning off), +0x14 / +0x18 ON and OFF lengths (the storyboard lengths in frames / 30), +0x1c hold time, +0x28 clock time of the last state change, +0x2c the element `<name>_Count` (Studs_Count), +0x30 / +0x34 / +0x38 storyboards `<name>_ON` / `_OFF` / `_Tally`, +0x3c the texture `Sprites/CommonLEGO/Pickups_commonstud.tga`, +0x40 stud type 0..3, +0x44 the update count of the last change, +0x48 u64 displayed value, +0x50 u64 pending value. The init also registers sink 0 with `0x23ca00(x, y, 5.5, 0)` at the centre of the element.
- `SetDisplay(obj, type, lo, hi)` 0x22ddf4 (objdump): type 4 leaves +0x40, else stores it (and the type in the flag byte 0x5206b0 + 0x20b bits 2..4 for the Studs bar); stores the value at +0x48, the update count (0x241098) at +0x44; if the stud flag 4 is set the Studs bar calls `0x240fc0(obj, 2.0)`, other bars with a value != 0 `0x240fc0(obj, -1.0)`. 0x240fc0 calls the generic show routine 0x23cc00 (ev_8d8eaf0a…; sets +0x1c = hold, state 0 -> 1 and +0x28 = clock; state 3 -> 1 with the ON time continuing from the OFF progress, `+0x28 = now - (1 - progress) * ON`).
- Per update the generic overlay machinery moves the state: ON storyboard length, then the hold of 2.0 s from the moment state 2 began, then OFF. Oracle (`bar1.mem`, tools/oracle/hud-bar.txt): the value 10 was banked in update 25 of the trace (state 0 -> 1, +0x28 = 228.733), state 2 from update 27 (+0x28 = 229.267), state 3 from update 35 (+0x28 = 231.4), state 0 from update 37. The stepped game clock advanced 0.2667 s per update (+0x28 values), so these are ON 0.5 s, hold 2.0 s, OFF 0.5 s; the layout's `Studs_ON` and `Studs_OFF` are 0.5 s. While the state is not 0 the bar's draw callback 0x166e08 (ev_24615f76…) runs; hidden bars draw nothing (checked: no digits at the top of the oracle screen while hidden).
- Drawing, 0x166e08 (when the displayed value is not 0): the element's screen position and size give the anchor (x + w/2, y + h/2) where y follows the `Stud_Count` translate of `Studs_ON` / `Studs_OFF` (from -14.5 hidden to 38.5 shown); the number is the u64 printed with `%llu` (0x235c18, format at 0x235c94, no separators) in the front-end font, white, centred on x, top at y; its width (0x235538, `%d`) places the icon: left x0 = x - (width / 2 + 32 + b), top y0 = y - b / 2 + 2, size 22 + b, with `b = 8 * sin(0.2 pi n)` for n = updates since the change while `update count - 5 < change count` (unsigned: while the update count is below 5 the bounce is off) else 0. The icon is the 4x4 sheet `Pickups_commonstud` (cell = `(int)(clock * 15)`, column = frame & 3, row = (frame & 15) >> 2), tinted per type with the colours of the world studs (0xffeeeeee, 0xff24bcff, 0xffff4240, 0xd0ff42a0). Sink 0 is set to (x0 + b / 2 + 11, y0 + b / 2 + 11), the icon centre, on every drawn frame.
- Number spacing: the front-end default -2 draws the digits 2 px too close; the oracle's number matches spacing 0 (mean abs over the number pixels 5.8, against 38 for -1, 68 for +1 and 109 for -2). `kStudNumberSpacingFitted`; the call that sets it was not identified (0x255244 / 0x2551cc(font, 4, 5) in 0x166e08 set font state).
- **No roll-up for pickups.** The pickup path banks the value in 0x28a128 (adds to 0x593418 and clamps at 4,200,000,000) and then the hook `*0x377298` = 0x29c090 (ev_5e552328…; the pointer 0x377298 was read in the oracle) runs: for the stud types 0..3 it calls `SetDisplay(0x519760, type, new counter)`, so the bar shows the new total at once and bounces; type 0xff (a value from a table) adds `u16(+4) * u16(+6)` with the multipliers of `0x2369a8(0..4)` and shows it the same way; type 6 adds to the second counter 0x593430. The only delayed path is 0x1584e0 (reached through a function pointer, probably the script function `AddStuds`): it shows the old total, adds the amount to +0x50, and 0x166e08 adds the pending amount to the displayed value and to 0x593418 once the state is 2 and more than 1.75 s have passed since +0x28 (`0x3fe00000` compare at 0x1673b4). That path is not replicated (no scripts run).
- Counters: 0x593418 (low) / 0x59341c (high) the stud total, 0x593430 a second counter (kind not identified) that 0x193604 draws as a floating number near sink 2 (colour 0xff00ffff, same 5-update bounce, delayed add of 35 updates), 0x593420..0x59342c the level target, 0x593438 bit 0 the "bar full" flag (set in 0x28a128).

### Flying studs (0x180168 state 4)
- A collected record (state 4, timer +0x3c = 1.0) moves every update (ev_cb51b368…c9ac468, pseudo-code of the state 4 branch): `timer -= dt`; while `timer > 0` the sink of the type (`table[type + 0x5c]`, 0 for all stud types, read in the oracle) is turned into a world point with 0x24c1d0 (ev_c9cd0506…) and the record moves `(target - position) / (30 * timer)` where 30 is `FUN_0023ca4c()` (0x23ca4c returns 30 when the thread's frame-rate object is absent; 0x376af8 +0x8 and +0x10 are zero in the oracle); when the timer is <= 0 the value is added (0x28a128) and the hook runs. The record is drawn as an ordinary stud sprite by 0x1c3fe4 (blend mode pair 4,5 for state 4, 1,0 otherwise; not decoded).
- 0x24c1d0: view-space x = `(sx / 200 - 1) * depth / xScale`, y = `(1 - sy / 120) * depth / yScale`, z = depth, moved to the world by the camera node's matrix; `yScale` / `xScale` are the projection words of camera + 0xc0 / 0xbc (camera.md: y scale = cot(fov / 2) * 4/3, x scale = y scale / aspect, aspect 400/240; screen size = 0x529e74 / 0x529e78 of screen 0). Sink table at 0x58ef4c, 12 bytes per sink (x, y, depth): the oracle holds (203, -14.5, 5.5) for sink 0 (the centre of `Studs_Count` while the bar is off), (76, 19, 5.5) and (186, 21, 5.5) for sinks 1 and 2 (set in 0x2cedb8). Studs collected while the bar is hidden therefore fly to a point above the screen; while it is shown they fly to the icon.
- Verification against the trace (`bar1.mem`, 15 updates at dt 0.07): the implied target of each step converges to (864.610, 20.836, 1064.381) once the camera has settled; the camera read in the oracle (eye K+0x34 = (867.3656, 20.0990, 1069.3754), look K+0x94 + K+0xf4 = (862.5931, 18.3988, 1060.5876), yaw -2.6441, tools/oracle/hud-camera.txt) unprojects the sink (203, -14.5, 5.5) to (864.6103, 20.8361, 1064.3806). Replaying updates 19..24 with that target reproduces the recorded positions to 2e-3 (the last step overshoots the target exactly as recorded). Tests: `studs-core` (`flight`, `unprojection`, `bankedTotals`).

### Bottom screen (map)
- The in-game bottom screen is the level's map texture `sprites/ui_bottomscreen/maps/<level>.btga` (1024x1024) turned so that the camera looks up the screen, with the player's arrow (`maps/playericon`, rotated by player yaw - camera yaw) at (160, 118) and the characters button of `sprites/blend/mapbuttons/mapbuttons.bxaml` (`buttonChars`, 64x64 at (0, 0), reference `button.bxaml` with `buttonIcon_chars`) at the top left; the other buttons of that layout are slid off screen. The oracle also shows the objective marker (`mapiconmission` with a ring) at the mission target. The map screen code (0x2dc590, ev_5b7590…) creates a `minimapscene` with its own camera, the map icons from the table at 0x3588a0 and the `mapButtons` layout; the in-game drawing of the map and the transform file `maps/<level>.txt` (21 floats: a 4x4 matrix with scale 1.6008 and 1337.4733, then 1.6008, 1.6008, 1337.4733, 1024, 1024) were not decoded.
- Fit (stand-in `kMapTexelsPerUnit`, `kMapOriginU/V`, `kMapPlayerScreenX/Y` in src/frontend/minimap.hpp): normalised cross-correlation of the oracle's bottom screen with rotated and scaled copies of the map found, for four positions (886.764, 1111.166), (960, 1111.166), (886.764, 1190), (866, 1066), rotation = camera yaw (-135.0 deg at yaw -2.3501, 114 deg at 1.9837, -6 deg at -0.0988), no mirror, 1.55 screen pixels per texel and the texel (594, 261), (641, 261), (594, 210), (581, 289): so one world unit is one screen pixel, u = 22.03 + 0.645 x, v = 977.7 - 0.645 z. The native map with the oracle's camera yaw differs from the oracle by 3.1 and 2.7 mean abs (pictures without the mission icon and the button, `metrics.json`), the arrow lies within 1 to 2 px.
