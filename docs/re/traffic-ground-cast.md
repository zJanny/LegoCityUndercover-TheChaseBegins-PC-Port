# Traffic: the ground ray cast and the colour message

Subtopic of [traffic.md](traffic.md): the ray cast behind the traffic probe 0x20ae2c (0x22b108, 0x266834, 0x22f978, the vertical tree walk 0x293188), the colour message 0x23e110 with its handler for mesh nodes, and the path name lookup 0x23895c shared by three users. The probe itself, the triangle weights and the colour are in [traffic-ai-driver.md §2026-11-03T08:37:32](traffic-ai-driver.md#ts-20261103-083732). Feature file: [pedestrians-traffic-cars-movement.md](../plans/features/pedestrians-traffic-cars-movement.md).

## Current state

- The probe's ray is vertical (x and z of both ends agree), so 0x22f978 takes the vertical tree walk 0x293188, not the general walk 0x265c34. It is a triangle test of its own: only front faces of the plane (the determinant is the y component of the triangle's cross product for a downward ray) and a hit ends the walk at the first triangle in tree order, not the nearest. [§2026-11-07T12:11:38](#ts-20261107-121138)
- The descriptor of the probe has include mask 1, exclude mask 0, no surface mask and no excluded owner. Entries with mask 17 (vehicle boxes) are therefore accepted as well as the static level (mask 1). A box that the segment meets ends the cast with no triangle, so the probe sends nothing. The first accepted entry that is hit ends the cast. [§2026-11-07T12:11:38](#ts-20261107-121138)
- Every collision item of the 3113 shipped models has an empty colour block and a 4-byte flag block whose word is 0, so the colour of the hit always takes the branch without a colour table (the three bytes +0x1d..+0x1f of the triangle are the grey values of its corners). [§2026-11-07T12:11:38](#ts-20261107-121138)
- The colour message (command 1) reaches the mesh node class handler 0x106980: for a mesh node it stores the colour's three low bytes at node +0x118..+0x11a. [§2026-11-07T12:11:38](#ts-20261107-121138)
- A path is looked up by the part of its name after the last `.` (0x23895c); the port does this in one helper `assets::pathNameHash` for the junction fill, the DCam paths and the pedestrian path count. No shipped count changed. [§2026-11-07T12:11:38](#ts-20261107-121138)

## 2026-11-07T12:11:38+01:00 — The vertical ground ray cast, the colour message on a mesh node and the path name lookup (llvm-objdump only, no REA session, no emulator; 20261107-traffic-D)

Method: `llvm-objdump -d --triple=armv6k-none-eabi --mattr=+vfp2` on `artifacts/game/game.arm.elf` (code read to the end: 0x20ae2c, 0x22b108, 0x22f978, 0x266834, 0x293188, 0x270534, 0x23e110, 0x228528, 0x106980 up to the colour case, 0x114640 and 0x23895c). The collision item blocks were counted over all 3113 models with the C++ loader. Port: `src/runtime/traffic_ground_world.*` (test `traffic-ground-world`, `traffic-ground-world-real-data`), `src/assets/path_name_hash.*` (test `path-name-hash`).

**Descriptor of the probe (0x20ae2c).** The stack record is the descriptor class of [pedestrians-inputs.md §2026-10-20T14:11:29](pedestrians-inputs.md#ts-20261020-141129) with the words include 1, exclude 0, kinds include -1, kinds exclude 0, owner +0xc include 0 and exclude 0, owner +0x10 include 512 and exclude 3, excluded owner 0, mode byte 1, and the surface mask (+0x30, +0x34) 0. It differs from the pedestrian's dodge ray only in the exclude word (0, not 16).

**Ray cast 0x22b108 -> 0x266834.** 0x22b108 gathers the grid entries (0x237f30) in the box around the segment and calls 0x266834. For each gathered entry in order: the segment is moved into the entry's space, then by kind. A box entry (kind 0, no composite owner) meets the segment through 0x2040e8: a hit leaves the out record's triangle 0 and ends the cast with 1. A mesh entry (kind 1) calls 0x22f978(item, from, to, out point, out triangle slot, surface mask, mode 1). A hit ends the cast: the point is copied back through the entry's matrix, the owner is stored in the out record, the result is 1.

**0x22f978.** Clears the triangle slot. When x or z of the two ends differ it calls the general walk 0x265c34 (not read). Otherwise the direction is (0, -1, 0) when the end is not above the start, else (0, 1, 0), the length is the y distance, and it calls 0x293188.

**Vertical walk 0x293188 (node recursion, mode 1).** Node test 0x270534(from, to, node): with d = from - centre, miss when |d.x| is above half x or |d.z| above half z; for y with e = to.y - centre.y: when d.y is below -half.y it misses when -half.y is above e; then it hits when d.y is at most half.y, else when half.y is at least e. A leaf (info bit 0) tests its (info & 0x1f) >> 1 triangles from index info >> 5; an inner node recurses into its children from index info >> 5 (nodes 0x1c bytes, triangles 0x20 bytes, both in chunks of 1024). The first hit returns 1 at once (mode 1).

Triangle test (corners v0, v1, v2 from triangle +0x10 / +0x14 / +0x18, surface byte +0x1c tested against the 64-bit mask with `1 << surface` by 0x2467c0, mask 0 here): e1 = v1 - v0, e2 = v2 - v0, dy = direction y, p = (dy x e2.z, 0, -(dy x e2.x)), det = e1 . p (0x257e78, single precision, no fused multiply-add: (a0 b0 + a1 b1) + a2 b2). Miss when the bits of det, as a signed integer, are below 0x3727c5ac (1e-5). o = from - v0, u = o . p, miss when u < 0 or u > det; q = o x e1 (0x23b960), v = dy x q.y, miss when v < 0 or u + v > det; t = (e2 . q) / det, miss when t < 0 or t above the length. On a hit: out point = from with y + dy x t, triangle slot = the triangle (the slot's second word is t). For a downward ray det equals the y component of e1 x e2, so a floor triangle must run counter-clockwise seen from above; triangles seen from below and steep ones are missed.

**Colour of the hit.** The probe passes the triangle and the owner's item (the entry's +0x1c) to 0x221064. The loader 0x114640 reads five blocks per item: name, a block B, a block C, the node chunk table and the triangle chunk table; item +4 is B when B is not empty, else C, and item +8 is the first word of C. In all 1725 items of the 3113 shipped models B is empty and C has 4 bytes holding 0, so item +8 is 0 and the colour is the weighted grey of the triangle bytes (+0x1d..+0x1f), not a table lookup. Distinct byte triples exist (52107), so the grey differs per triangle.

**Colour message.** 0x23e110(node, colour, -1, 1) stores {colour, -1} and calls 0x228528(node, 1, args, recursive). 0x228528 calls the handler at +0xc of the 16-byte class slot of the node (table 0x5303c4, class = node word & 31) as handler(node, command, args), then, when recursive, the same for each child (+8 first child, +0xc next sibling). The mesh node type registers 0x106980 (registration 0x103290). Its case 1 (0x1069e8) runs only for a node of the mesh class, and for each of the two layers (+0xc0 + 4 i) that has mesh data: with the second argument -1 it stores the colour's bytes 0, 1 and 2 at node +0x118, +0x119 and +0x11a, and, when the layer's word (+0x104 + 4 i) is set, sets the three colour bytes of every vertex of the layer (stride 0x60 from +0x10) to 255. Which classes the car's node tree holds, and where the draw reads +0x118 / +0x11a, were not read.

**Path names (0x23895c).** Confirmed from the code: the scan keeps the index of the last `.`; with an index other than 0 the part after it is hashed, otherwise the whole name. `assets::pathNameHash` does this; the junction fill's path lookup, the DCam path lookup and the pedestrian path count use it. The shipped counts (`traffic-junction-fill-real-data`, `pedestrian-system-real-data`, `dcam-real-data`) did not change.

**Port.** `castTrafficGround` (levels' collision world, kind and order as above), `trafficGroundWorld` (the `TrafficGroundWorld` of the probe), `applyTrafficColourMessage` (the three bytes). Stand-ins TRAFFIC-S23 (entry order) and TRAFFIC-S24 (the receiver). On the 4383 path points of lvl_01 the probe finds a triangle at 3884 (port output of 20261107-traffic-D, level data only; no original value was compared, a regression pin in `traffic-ground-world-real-data`).
