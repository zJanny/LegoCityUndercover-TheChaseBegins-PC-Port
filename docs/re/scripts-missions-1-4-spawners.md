# Mission 1-4: the AI spawner class

The AI spawner class (kind 14, `props/prop_aispawner`) that holds and releases the characters of the missions, the spawners of the eight main levels and the spawner chain of mission 1-4. Split from [scripts-missions-1-4.md](scripts-missions-1-4.md). Items: [script-system-missions-1-4.md](../plans/features/script-system-missions-1-4.md).

## Current state

- The mission is a chain of AI spawners: each spawner holds its characters (disabled, word +0xc bit 4) from the post-link until it is triggered, releases them one by one and, once every slot has spawned and (with `WaitForDead`) every character has bit 4 again (defeated or arrested), fires the object named by its `TriggerObject` parameter. All eight spawners of the mission have `StartActive` 0, `StartSpawned` 0 and `SpawnFromSpawner` 0. The class (create, post-link, handler, update, state change) is read and ported for all 109 spawners of the eight levels; the spawned character's StartState and the view test are not. **What makes a slot done.** Bit 4 of the character's word +0xc set again: by the destroy 0x23cd80 when the class answers message 1 with 0, and by the arrest 0x21ddb8 (it raises *0x375ff8 for the character and the player, then 0x241304, bit 4, 0x24ce78 and 0x2428c0). In the port a character defeated through the hit receiver reaches 0x23cd80 (`destroyEntity`); the arrest is not ported (SCRIPT-411). Bit 4 lives in two places in the port: the spawner reads `PlacedObjectState::destroyed`, while the hit kill and the arrest write `CharacterHitTarget::destroyed`; the arrest must also reach `PlacedObjectState::destroyed`, or a spawner never sees its arrested goon as done.

**Who triggers `1-4_Spawner_01` and `1-4_Pursuit_Booster_Spawner` (SCRIPT-417).** Nothing in the data: no script call of lvl_01 names them, no reference record has them as target, no object parameter of type 4 names them, and both have `StartActive` 0, so the class never starts them itself. The executable holds neither the names nor their name hashes (0x7c68c19d, 0x2b3be370), and none of its strings contains "1-4_". So goons 01 and 02 and `Booster_Strange_02` stay held (disabled) for the whole level, and `1-4_Pursuit_Booster_Spawner_Script` (CharacterArrested of `Booster_Strange_02`) can never run: like `1-4_AI_HeadRobber`, leftovers of an earlier design.

**In the port** (`src/runtime/ai_spawner.*`, glue `src/runtime/game_ai_spawner_glue.cpp`). The rules above run for every kind-14 object; held is the port's `destroyed` set plus `disabled`, the release puts the character's node at the matrix and clears both. The spawners update in the objects phase after the switches; the order of the class updates in the original was not read. Not applied (stand-ins SCRIPT-S321, SCRIPT-S322): message 53, the reset 0x218b88 and message 2 of message 52, the controller tests (+0x16c, +0x6e), the heading and +0x314 bit 6, the StartState entry (the character stands where it came out), the view test (a `SpawnOnScreen` 0 spawner spawns as if out of view), the skip of the bound test, the clips and the 0x2320f8 calls of states 0 and 3 (no effect without a mesh), `StartEffect`, the sound, the reveal object's move and message 51.
