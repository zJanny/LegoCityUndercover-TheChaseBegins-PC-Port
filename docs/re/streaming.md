## 2026-10-13T22:27:00+0200 — World levels, room links, scene change chain (REA Ghidra 12.1.2, llvm-objdump `--mcpu=arm1176jzf-s`, Azahar oracle port 24691 without RPC)

**Corrections of earlier entries**
- [levels.md 2026-10-12T23:25](levels.md) says the game's streaming is `Pregen/*.bin`. Wrong: `pregen/` holds `collectables_level1..7.bin` (71 bytes each), `customchar.bin`, `levelobjectscount.bin`, `traffic/lvl_*_traffic.bin` and `pedestrians/lvl_*_pedestrians.bin` (AI route data for vehicles and pedestrians; code strings `Pregen/Traffic|Pedestrians/%s_*.bin` 0x2... in [arm-executable.md](arm-executable.md), `pregen/Collectables_Level%u.bin` at 0x23b598, `pregen/CustomChar.bin` at 0x1b7730). They are not read by anything that loads rooms. Not decoded here; the streaming data is the level file section +0x34 (below).
- The game does not load "one whole level" as the port does. The city is a master level plus world levels (below); the port's ASSET-S2 composition by archive folder is a stand-in.

**Room links (level section +0x34, decoded)**
- Loader 0x1cfc50 reads a header block (u32 count, pointer), a record block and one list block per record. Record 0x10 bytes `{u32 room hash, u32 world level hash, u32 entry count, pointer}`; list entry 12 bytes `{u32 room hash, u32 world level hash, u32 1}`. Hashes are `nameHash` of `RoomN` (capital R, no zero padding) and of the world level instance name. Present only in `lvl_the_city.blvl` (309 records, per world level 3/43/12/51/40/56/44/60 for policestation..downtown), `lvl_05_bluebellwood_main.blvl` (54 records, world level hash 0, all lists empty) and `lvl_00_policestation_main.blvl` (1 record, empty). No entry leaves its world level; every flag is 1.
- Consumer 0x173f94 (run after a level is built): for each record whose world level hash equals the hash of the current world level name (r11+0x18) it finds the room (a record room hash equal to the hash of the literal "root" at 0x359130 selects the level's root object) and calls 0x1ddae4(room, count+1) and, for every list entry, the neighbour lookup 0x22d64c and the link builder 0x22cf94/0x22d0f8. The same function also looks up rooms by the names "Room1".."Room200" (format "Room%u" at 0x174420, ctor reads 0x1741a8, 0x1742ac).
- Data fit against the oracle: the links of `WorldLevel_01_CherryTreeHills` Room8 are Room1, 2, 3, 7, 9, 14, 15, 16. With Room8 itself they are exactly the first nine loaded rooms of the oracle list. Rooms 17, 22, 23 are also loaded; they are linked from Room16 (17, 22, 23) but the other neighbours of Room16 (10, 21) are not loaded, so the full rule is not known.
- The room links are symmetrical in the checks done by eye for Room8/9/14/15/16; not pinned.

**Room streaming objects and natives**
- Classes `roomstreamingcontrol` (`leGORoomstreamController`, ctor 0x28f148, string at 0x28f1ec) and `roomstreamingdestination` (0x29c86c). The controller holds up to 15 rooms from the string parameters `RoomToStream01..14` ("RoomN", 4-char prefix compared, number by 0x203564) looked up in the level room array (scene+0x1320); its handlers call 0x20f194 per room (append to the global request list 0x375d70: u32 count, pointers) and the consumer 0x2b9cf8 hands each request to 0x205b5c. The destination objects carry two string parameters (hashes 0x2e0a8af5 and 0xb703db4f, both "RoomN"). In lvl_01 only two pairs exist (rooms 40/34 and 7/8) and lvl_03 two (Room31; Room17/16): a scripted use, not the general walking case.
- Script natives: `StreamRoomIn "RoomN"` handler 0x1bfba4 (finds the room in the current level by name, 0x20f194 request, returns 1 once 0x2284bc says loaded, else blocks), `RoomStreamingWait <controller>` handler 0x27bde0 (-> 0x2a51bc), `DebugLoadRoom/DebugUnloadRoom`. Uses: lvl_01 mission scripts `1-2_Cage_Key_Target_Script` (Room40), `1-4_RobberCaught` (Room17), `1-8_MissionEnd` (Room8), `Race01*` (Room9, Room3), similar race scripts in lvl_03/04/05.
- "RoomStreamLogic" (string 0x34eebc, registered by 0x34ee90, vtable 0x363e98) has a no-op update (0x3095a8 is `bx lr`), so the logic class itself does nothing; the real work is in the level/room objects above.
- What decides, per update, that the player's room changed and its link set is loaded or dropped was not found (see unknowns).

**Level switch chain (code)**
- Script native `SceneChange <bound>` (table entry, handler 0x1b262c) calls 0x26344c(bound hash): scans the entity list of the current level (`[0x...+4]`, count +0x1c, array +0x24) and then the master level's list (`[0x3772c0]` side, +0x28) for an entity with type byte 78 (0x4e, class `scenechange`, ctor 0x1c46dc "leGOscenechange", params `SceneChangeBound`, `SceneChangeTo`) whose bound hash (0x20c1a8 of its +0x7c data) equals the argument, and sends it message 0xff via 0x244fc8 (the same message that opens doors). A level script's bound argument is therefore resolved against the scenechange objects of the master level `lvl_the_city` (qualified name `WorldLevel_NN_X.<bound>`; how the qualifier is added is not read).
- The scenechange object's handler 0x1c47e8 resolves the destination entity (0x2234a8 or the `SceneChangeTo` reference), the destination room and then calls the global manager (vtable slot +0x28 or +0x2c of the object at 0x37758c, flag byte +0x30 set by the ctor).
- Execution 0x303480(request) (REA ev_52dfea92…): destination entity [request+0x28]; the scene index is byte +0xd of that entity (0 selects the default scene 0x589a1c, else array 0x589a18+4). `0x2284bc(scene)` tells whether the destination world level is already loaded. Not loaded: progress 0% -> "OnSceneExit" event (0x1ecc50, 0x198058), 25% (0x41c80000) free the old scene (0x204598, 0x1e774c), `0x2e3cc4(&0x5863b4)` tear down the world and `0x2e3a9c(&0x5863b4)` create it again, 0x223878(scene, 0) start loading and 0x21ac70(scene) wait for it, 50%, then the player is placed at the destination (0x213284 returns the room and the matrix; 0x24c118 writes the player node), 100% progress, "OnSceneEnter" (0x1ecc50), 0x1f23f0 is the loading-screen progress setter (floats 0..100). Already loaded: the player is only moved.
- `0x2e41e4` (vtable 0x362014 slot +8, enter of the gameplay mode object built near 0x343e00, update 0x2e5158, leave 0x2e3e98) is the initial level load: it formats `levels/%s/%s_main` and `levels/levels/%s/%s_main.blvl` from the level table name, loads the world, runs the progress setter, finds the room list and `Room%u` objects (0x173f94), places the player (0x2e6264) and returns to the update. The earlier "loader at 0x1cfc50" is the generic `.blvl` deserializer it uses.
- Level scripts: lvl_01 `Police_ExtToInt` (building entry from the street): `WarningDialogBox DIALOG_RETURNCODE`, on 1 re-arm triggers, on 2 `Entered_Police_Station = 1`, `PositionObject`, a camera track, `AIMove` into the door, `TriggerObject Police_Door_01/02` (doors), `Wait 3`, `SceneChange Police_ExtToInt`. Entry through the helipad: `Police_Station_Transition_Upper` ending in `SceneChange SceneChange_Helipad_To_Lobby`. City-to-city by vehicle or on foot: `CTH-AUB_Foot_Transition` etc. with `FadeScreen 0`, `PositionPlayer Player1 <point>`, `SnapCamera`, `FadeScreen 1` and `SceneChange SceneChange_Cherry_To_Auburn`. 24 `SceneChange` calls exist in the shipped level files (lvl_01 8, lvl_02 1, lvl_03 2, lvl_04 2, lvl_05 2 and others); 40 `StreamRoomIn` and 9 `RoomStreamingWait`.
- lvl_00 (the police station) has its own `scenechange` objects for lift travel between lobby (room1), basement (room3) and lineup (room5): `Lobby2Basement_SceneChange`, `Basement2Lobby_SceneChange`, `Basement2Lineup`, `Lineup2Basement`. Scripts enable and disable their bounds with `EnableBound` (the lift scripts `LIFT_Lobby`, `LIFT_basement`).

**Event bindings (level section +0x1c, decoded)**
- Record 0x18 bytes plus five string blocks: object name (+8; empty for bound events), script name (+0xc), event name (pool -16), two arguments. Events seen in lvl_01: ObjectTriggered 123, BoundEntered 62, ObjectBoundEntered 23, PlayerRaceVehicle 19, PlayerOnFootBoundEntered 10, OpponentRaceVehicle 7, PlayerVehicleBoundEntered 5, BoundLeft 4 and others (names of `levels/letriggers.txt`). Example: the on-foot bound `Police_Station_Transition_Lower` (centre (907.24, 18.23, 1115.9)) runs script `Police_ExtToInt` on `PlayerOnFootBoundEntered`; `BoundLeft` of the same bound runs `Police_ExtToInt_SwitchOn`. Counts: lvl_01 241, lvl_00 53, lvl_05 221.
- Section +0x24 (bounds) records have a byte tuple at +8 (for example `01 04 01 01`, `ff 03 01 01`) that is not decoded.
