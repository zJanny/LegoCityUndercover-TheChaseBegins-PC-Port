## 2026-10-15T15:10:38+02:00 — OverrideMusic, AutomaticMusic, StopMusic, EnableTrafficAndPedestrians and the readers of camera manager +0x28 (llvm-objdump only, no REA session, no emulator)

Method: `llvm-objdump -d --triple=armv6k-none-eabi --mattr=+vfp2` on `artifacts/game/game.arm.elf`; handler ABI as in [script-natives.md](script-natives.md) (r1 = argument pointers). Replica: `src/runtime/natives_music.*` (`MusicNativeState`), `ProgressNativeKind::EnableTrafficAndPedestrians`; tests `natives-music`, `natives-progress`.

**Music block 0x376b30** (all fields by the disassembly of 0x240ec8, 0x24039c, 0x1c29ac, 0x22b660, 0x240f6c, 0x240f5c, 0x1a4d7c): +0 byte stream-queued flag, +1 byte override active (set by 0x240ec8, cleared by 0x1c29ac, read by 0x240f5c), +2 byte volume ramp active, +3 byte mood (0x1a4d7c returns it; the earlier entry's DAT_00376b33), +4 / +5 loop and crossfade flags of the last track request, +6 hword (0x240ec8 skips the start while it is nonzero; writers not read), +8 hword track id, +0xc master music volume (float), +0x10 pointer to the array of track names, +0x18 lock (0x25c828 lock, 0x25c5c8 unlock around changes), +0x1c stream handle, +0x20 fade-out step, +0x28 last fade.

**OverrideMusic 0x1cdb28.** `0x240ec8(id = (u16)*(u32*)arg, loop = 1, crossfade = 1, fade = 0.5f)` (literal 0x3f000000 at 0x1cdb50), returns 1. 0x240ec8 stores id, flags and fade in the block, copies the name `((char**)*(u32*)(block+0x10))[id]` to 0x5862e8, and when the hword +6 is zero locks, sets the override byte +1 to 1 and calls 0x24039c(name, id, loop, crossfade, fade). 0x24039c with crossfade 1 and a stream already named at 0x5861e0 does not start: it queues name, id, loop and fade (0x586230, 0x586270, 0x58627c, 0x586274), sets the ramp byte +2 and the queued byte +0; a per-frame updater (not read) must start it. With no stream, or crossfade 0, it stops the current stream (0x21cc04(0)) and opens `Music/<name>.wav`; with crossfade 1 the new stream starts at volume 0 and ramps to the target (+2 set, target 0x586224 = fade), with crossfade 0 it starts at fade times the master volume.

**AutomaticMusic 0x1d9c70.** `0x1c29ac` clears the override byte +1, then `0x204fe0` (also entered by the tail jump at 0x26aa50 from 0x26aa30, a routine that decrements the hword at its first pool word and sets a byte; its callers were not read), returns 1. 0x204fe0 returns at once while the override byte is set (0x240f5c), while the director camera is busy (0x236104) or while byte 0x374264 is set (0x2c7bbc). Otherwise it scans the six entries of the table at 0x58deb0 for a live one whose component flag byte +0xd8 has bit 5 and whose distance to the player (node +0x30) is below float(hword component +0x7a): that sets "combat" and clears the counter byte 0x374304. With combat (or byte 0x374305 set) and mood byte +3 clear it calls `0x206c40(fade 1.0, mood 1, 1, 1)` (action music) unless 0x22b0b4 (byte 0x5163e8+0x25 equals 1) holds. Without combat it does nothing unless the mood byte is 1; then, when 0x22b0b4 and the sudden-start bit (0x173754) are clear, it counts 0x374304 up and calls `0x206c40(1.0, mood 0, 1, 1)` once the count exceeds twice the value of 0x23ca4c. So a call with mood 0 and no combat only clears the override byte.

**StopMusic 0x195054.** The argument is a float. 0.0: `0x21cc04(1)` (locks, stops and frees the stream 0x376b4c, clears the name block at 0x5861e0, clears the handle). Otherwise `0x240f6c(1.0 / (30.0 * arg))` (step stored at +0x20; a step of 0 or below is replaced by the literal 0x3ca3d70a = 0.02) and `0x22b660(0.0)`: sets the ramp byte +2 and the ramp target 0x586224 to 0. The per-frame ramp that applies the step is not read; 30.0 suggests an update rate of 30 per second (inference). The override byte is not changed.

**EnableTrafficAndPedestrians 0x2c5780.** With flag = (word of argument 0 != 0): `0x2b476c(flag)` sets bit 1 of byte 0x51b3e0 (0x51b33c + 0xa4) and `0x29f09c(flag)` sets bit 1 of byte 0x5277a0 (0x527410 + 0x390); returns 1. Both objects are managers with a pointer list from +0x40 (traffic: count +0x90, spawn limit +0xa0, countdown +0xa8; pedestrians: count +0xc0, countdown +0xda0). Their init (0x2ee4b4, 0x2dfa48) sets bit 1, so spawning is on by default. The update of the traffic manager 0x2ee5e8 and of the pedestrian manager 0x2dfe88 read it: with bit 1 set, and bit 0 set, they count the live entities and spawn new ones while below the limit (0x2ee068 and the pedestrian equivalent) after the countdown; with bit 1 clear every live entity is removed (0x2428c0 on traffic cars; pedestrians first get message 0x80000006, then 0x2428c0) and nothing spawns. The port has no traffic or pedestrians (SCRIPT-230); the flag is recorded only.

**Readers of camera manager 0x376870 +0x28 (CAMERA-22).** +0x28 is the requested camera, +0x2c the current one (+0x30 the previous). The manager update 0x23f174 reads both: when +0x28 differs from +0x2c it calls the current camera's virtual at [vtable+4] (leave), moves current to previous, makes the requested camera current, stores its type byte (+0x18) in manager byte +1 (calling 0x2c8864 when the type changed) and calls the new camera's [vtable+0] (enter); every update it then calls the current camera's [vtable+8] (update). A request equal to the current camera does nothing. CameraFollow 0x1bf7c8 therefore asks for the camera object `*0x3770d8` (the same object the level start passes at 0x182170). The nine writers pass different camera objects (globals 0x3770d8, 0x3771f0, 0x377288, 0x3772c0 and others), so CameraFollow is a camera switch request, not a flag. Whether the port's no-op equals it depends on which camera is current at the call; mission 1-1 calls it at the end of `1-1_VanBreakdown` after the cutscene `1_1_b`, where the port ends the cutscene camera by its own hand-back.

Unknowns:

- Value of 0x23ca4c (the frame threshold of the action to ambient return); what 0x22b0b4's byte 0x5163e8+0x25 is.
- Which camera is current when CameraFollow runs in 1-1, and the vtable entries of the camera classes (enter, leave, update).
- The spawn rule of traffic and pedestrians (0x2ee068, countdown, limits).

## 2026-10-15T16:33:19+02:00 — Music block updater 0x240c3c, start 0x24039c, mood route 0x206c40 and the level-start call (llvm-objdump plus oracle memtrace, no REA session)

Method: `llvm-objdump -d --triple=armv6k-none-eabi --mattr=+vfp2` on `artifacts/game/game.arm.elf`; oracle (`tools/azahar_oracle.py`, state `m11-6-van-to-shop`, OpenGL renderer; the software renderer crashed in the rasterizer at load) with pokes and `memtrace`. Replica: `src/runtime/music_block.*` (`MusicBlock`), test `music-block`. Extends [the earlier entry](#ts-20261015-151038).

**Records.** Current track at 0x5861e0: path string "Music/<name>.wav" (+0, first byte 0 = empty), id hword +0x40 (0x586220), target float +0x44 (0x586224), volume float +0x48 (0x586228), loop byte +0x4c. Queued track at 0x586230 with the same layout (name, id +0x40, fade +0x44, loop +0x4c). Block +0 byte is set to 1 by the first queue and read as the crossfade argument when the updater starts the queued track (observed 1 in every m11 state and in street-after-1-1). Block +0xc master 0.8, +0x1c stream handle, +0x20 ramp step (0.02 from the init 0x17eb5c, 0.2 in m11-6), +0x24 set record pointer, +0x28 last fade.

**0x24039c(name, id, loop, crossfade, fade).** With crossfade and a non-empty current name: ramp byte +2 = 1, current target = 0, the queued record = (name, id, loop, fade), block +0 = 1, return. Otherwise: an open stream is stopped (0x21cc04(0)); id 0 returns (id 0 never plays); the duck record 0x5862d0 byte +0x14 is cleared and, if it was set, fade becomes 1.0; the current record gets path, id, loop, target = fade; the queue name and id are cleared; the stream is opened (0x22be4c, flag 2 when loop, 0 otherwise); on a failed open it returns with id and name kept; with crossfade the stream volume and current volume are 0, ramp byte 1, target fade; without it the stream volume is fade times the master and current volume = fade.

**0x21cc04(flag).** Stops and frees the stream, copies the current record to 0x586280 (read by nothing found), clears stream handle, id and the name's first byte; a nonzero flag also calls 0x168a28 (unread).

**0x206c40(fade s0, mood r0, loop r1, crossfade r2).** Returns at once when hword +6 is nonzero, override byte +1 is set or the set pointer +0x24 is 0. Entry 255: stores the mood; if the current id is nonzero it sets ramp byte 1 and target 0 (the stream keeps playing and fades out); then clears current id and name. Otherwise entry 0 swaps the mood; a track different from the current id is started: without crossfade 0x21cc04(0) first, then 0x24039c(name of the track, id, loop, crossfade, fade); the mood byte +3 is stored. The level start 0x2f71b0 calls it with fade 1.0 (literal at 0x2f705c), mood 0, loop 1, crossfade 1 unless a byte at (object 0x2f6c04)+0x185 is nonzero (unread); before it 0x1ecdd4 stores the set record (index byte +0x39 of the level record, below 14, else null) at +0x24. So lvl_01 (set 2, ambient 255) with nothing playing starts no music, as the earlier oracle reading showed.

**Updater 0x240c3c(dt)** (callers: the main loop 0x2d5928 with the update dt, 0x1587a4, 0x2f3564, 0x2faec8, 0x303ec4). Under the lock: (1) a stream whose state (0x220fe0) is 4 is stopped, the current record copied, id and name cleared; with the loop byte set it reopens from the (now empty) name: not replicated. (2) Duck record 0x5862d0 handling (flag +0x14 bit 0, countdown +8, sound handle +0xc/+0x10, restore value +4 after the countdown): not transcribed. (3) With the ramp byte set and no stream it goes to (5). With a stream: delta = step(+0x20) * N * dt when dt >= 0 (N = 0x23ca4c(), the update rate, 30 when no rate object is found), else step; with the duck flag set the step is 0.05 (literal 0x3d4ccccd). Target >= volume: volume + delta, above the target clamps to it and clears the ramp byte; otherwise volume - delta, below the target clamps and clears. The result is limited to [0, 1] (bit pattern of 1.0 compared as a signed integer), set on the stream as volume times master, and stored. (4) Only when target and volume are both 0 and the duck flag is clear it continues, otherwise it ends. (5) 0x21cc04(0), then 0x24039c(queued name, queued id, queued loop, crossfade = block +0, queued fade), then the queued name and id are cleared. With nothing queued this is a stop (id 0 returns).

**Oracle check (state m11-6-van-to-shop, ramp byte 0x376b32 = 1 and target 0x586224 = 0 poked, memtrace 14 updates, step 0.2, stream 0x08ff8520, id 16, volume 1.0):** per update dt 0.033333, 0.07, 0.07 gave volume 0.8, 0.38, then 0 with the stream handle 0, id 0 and the ramp byte cleared in the same update (delta = 0.2 * 30 * dt: rate N = 30 confirmed). In the next update the game itself restarted track 16 with the crossfade (new stream 0x08f90710, target 1.0, volume 0.42 after the update), then 0.84, then 1.0 with the ramp byte cleared. States m11-1, m11-2, street-after-1-1 and street-at-entrance have no stream (id 0); m11-6 is the only m11 state with music playing (id 16). The lock hword +6: no store to it was found among the users of the block pool word (0x376b30); it stays 0.
