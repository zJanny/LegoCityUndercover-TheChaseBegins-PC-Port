# Director camera (DCam)

Reverse-engineering findings for the script camera: level paths, StartDCam / StartDCamTrack, the phase machine, the busy test of WaitForDCam, the end and the hand-back. Entries are chronological; later entries may correct earlier ones. Evidence IDs are shortened with an ellipsis. Replica: `src/runtime/dcam.*`, `CameraRig::setDirector`; tests `dcam`, `dcam-real-data`.

## 2026-10-14T14:36:00+02:00 — DCam system, level paths, phase machine, end test, oracle traces (REA Ghidra 12.1.2, llvm-objdump `--mattr=+vfp3`, Azahar New 3DS states street-at-entrance and dcam-police-dialog; SCRIPT-28, SCRIPT-40)

Evidence IDs: 0x21cc80 ev_e7a3dd60…, 0x1883ec ev_a3290eb5…, 0x236104 ev_4cf670be…, 0x228ca0 ev_429c3d47…, 0x2297b0 ev_bc1f5c7a…, 0x2665e4 ev_c215ee32…, 0x271130 ev_0449919b…, 0x2240e0 ev_68b7e5be…, 0x189548 ev_be9ce0ec…, 0x22a3b0 ev_aeaa66f0…, 0x1c17c0 ev_ea2de85a…, xrefs of 0x3768c0 ev_af4e47db…. 0x2028c8, 0x202814, 0x2027c8, 0x235dc4, 0x23cb14, 0x196784, 0x2ae250 were read with llvm-objdump only.

**Where the data comes from.** The `path` arguments (script argument type 6, 0x211e04) resolve through 0x22a3b0: the first record of level section +0x20 whose u32 +0 equals the name hash (0x28-byte records, count u16 in the section head +10). Record: +4 optional block (room name), +8 type (sampler table 0x358f9c, entry of 5 words: 0 → 0x1c17c0, 1 → 0x1b33fc), +9 closed flag, +0xa u16 point count, +0x10 a value that adds two more blocks (not used by the DCam paths), +0x20 float -1 in every record; the points are a block of 12-byte vectors. lvl_01: 457 records, all type 0; the 257 camera and look arguments of its StartDCam / StartDCamTrack calls all resolve, all open, with 1 to 5 points (106 / 108 / 38 / 4 / 1). Decoder: `Level::paths` (`src/assets/level.cpp`). Type 0 (0x1c17c0) is a uniform Catmull-Rom spline: position t in 0..count-1 (clamped when open, wrapped when closed), `p1 (2t³-3t²+1) + p2 (-2t³+3t²) + (p2-p0)(t³-2t²+t)/2 + (p3-p1)(t³-t²)/2` with neighbour indices clamped (open). Type 1 (0x1b33fc) interpolates with 0x257f14 / 0x248850 (quaternion-like helpers) and is not used by any DCam path of lvl_01; not transcribed.

**Start (StartDCam 0x194fd8 → 0x21cc80).** Arguments are 8-byte slots {type, value pointer}: camera path (value+8), look path, snap (float → int & 0xff), time. 0x21cc80 picks a command by which of (camera path, look path, look object) are set: both paths → routine 0x2665e4; camera path + look entity → 0x271130 (StartDCamTrack 0x1da810 resolves the object with 0x22dacc); look path alone → 0x270ff4; one entity alone → 0x2879b0 (the last two not read). A command context is allocated with 0x224168 (+0x1c camera path, +0x20 look path or entity, +0x24 u16 curve 5, +0x26 reverse flag 0), initialised by 0x2240e0 (state 0 with the start wait D+4 when it is above 0, else state 1; timer +4, duration +0x14 = time), pushed with 0x224094 / 0x224080 (CAMERA-8 stack, header flag 1, curve 5, time = D+0x14 or 0 when snap bit 0 is set), then 0x189548 sets D+0x10 = D+0x18, clears D+4 and D+8 (so a start wait set before the call applies, an end wait set before it does not), sets D+0x24 bit 0 (active) and switches the current camera pointers 0x376898 / 0x37689c to the DCam camera (0x3768e8). Snap bit 1 sets D+0x10 (blend-out time) to 0. StartDCam also counts nesting in byte 0x3768bc; StartDCamTrack sets bits 1 and 2 of byte 0x56d558 instead (use not read). D (`*0x3768c0`) holds: +0 pool, +4 start wait, +8 end wait, +0x10 / +0x14 / +0x18 blend times (all 1.6 s at gameplay start), +0x1c FOV factor 1.0, +0x24 flags (bit 0 active, bit 1 end requested, bit 2 snap the end, bit 3 set by 0x189548's argument).

**Command routine 0x2665e4 (every update, with the stack update 0x2ae250).** Pose +0x30 FOV = 43 × D+0x1c (a hook at 0x3768dc may replace 43; none was set), +0x34 = 0.035, +0x38 = 8.0. Progress: 0x2028c8 returns 1 in states 0 and 1 (state 0: timer done → state 1, timer restarted with the run time; state 2: timer done → state 3). In state 0 the eased progress is 0, in state 1 it is the curve-5 smoothstep of elapsed / duration (0x235dc4: 1.0 and the timer stops when elapsed ≥ duration), in states 2 and 3 it is 1.0. Eye = camera path at progress × (count-1), look = look path likewise (0x271130 instead takes the look point from the entity: its matrix 0x221a1c, transforming the entity's offset at +0x60 with 0x250da8, and does not re-evaluate in states 2 and 3). The tail 0x202814 ends state 1 when the timer stopped: with D+8 = 0 → state 3 and "done" (returns 1), else state 2 with a timer of D+8. The timer is clock based (0x25cfc8, duration = ticks per second × time as u32, minimum 1); the replica assumes 1000 ticks per second and adds round(dt × 1000) per update.

**Busy test and end.** WaitForDCam returns `!0x236104`. 0x236104 = `0x2297b0(0)` (a cutscene is playing, SCRIPT-29) or (D+0x24 bit 0 and one of the current camera pointers equals the DCam camera 0x3768c4). EndDCam (0x17cbd4 → 0x228ca0(1)) does the same test and then sets D+0x24 bits 1 and 2. The stack update 0x2ae250 sets bit 3 of camera object byte +0xdd when the newest entry's routine returns done. The end test 0x196784 runs every update after the script runner and WaitForDCam: with D bit 1 or the done bit it clears D bit 0, writes the hand-back request {flag (0 when D bit 2: instant, else 1), time D+0x10, curve 5} to camera object +0x88 with +0xdd bit 2 (0x2c5918), switches the current camera back to the default camera (0x377110) and clears D bit 1. The camera manager applies the request one update later by pushing the gameplay command (follow 0x2a8bfc or record pose) again.

**Oracle (state dcam-police-dialog = street-at-entrance walked into Police_Station_Transition_Lower, dt fixed 0.033, A pressed; tools/oracle/dcam-police-entry.txt, -order.txt, -poked.txt).** Update 4 (first after A): the script runs `StartDCam Dcam_Enter_Station_Ground Dcam_Enter_Station_Ground_Target 3 4`; the stack top becomes the DCam entry (routine 0x2665e4, weight 1, stack cleared: snap start), D+0x24 = 5, D+0x10 = 0, FOV 43, +0x34 0.035, +0x38 8.0; eye (904.7454, 22.4841, 1106.5201) and look (906.4791, 18.1096, 1115.2775) equal the two one-point paths exactly; pose filter factors stay 1.0. Update 125 (121 updates later): camera +0xdd = 8 (done). Update 126: D+0x24 = 4, +0xdd = 0xc, current camera pointer back to 0x377110, stack still the DCam entry. Update 127: stack top is the follow command, weight 1, FOV 40. The trap on 0x1883ec / 0x1b262c / 0x196784: in every update the runner (0x169254, once per scene), then WaitForDCam, then the end test run in that order; WaitForDCam still blocks in the update of the end test and SceneChange (0x1b262c) runs in the next one (update 127 = 123 updates after the start). Timing fits the replica: 33 ms per update, first routine call with 33 ms elapsed, done when elapsed ≥ 4000 ms. With the script's path names overwritten in memory (measuring aid) by `Dcam_Police_Door` (two points) and its target, 122 updates of the eye agree with Catmull-Rom plus smoothstep to 1.6e-4 (`cmp` of the replica formula; pinned in `dcam-real-data`). Screenshot comparison: `artifacts/oracle/agentL-out/compare/dcam_police_oracle_left_port_right.png` (same framing; the player stands elsewhere in chase-game because AIMove is not implemented).

**Other natives of batch SCRIPT-28.** SetDCamStartWait 0x26fdf0 stores D+4, SetDCamEndWait 0x1da690 stores D+8. DCamActive 0x1a2e48 sets bit 1 of byte +0xd9 of the object's component (+0x7c) from its second argument (readers not found). Set3DFocusObject 0x288aa8 sets the stereoscopic 3D focus object (0x1ff394 / 0x1ff3a4); no mono effect. ShakeScreen 0x1b2690 passes (amount as three bytes, damp flag, seconds, 0) to 0x22c500. SnapCamera 0x1a30fc: when the current camera's controller is the follow controller (0x217b14) it calls the follow reset 0x2313c8(controller, 0), else 0x217b04(1). CameraFollow 0x1bf7c8 sets the current camera pointer to the default camera (0x226a30); CameraRotFixedSet 0x27bb9c ends a busy DCam (0x228ca0(1)) then calls 0x182060; VehicleSetDCamPathFollow 0x27be1c not read.

## 2026-10-15T09:37:12+02:00 — What an active director camera does to the characters, the clock and the player's controls (llvm-objdump `--mattr=+vfp3` on `artifacts/game/game.arm.elf`, REA not used; Azahar New 3DS state m11-2-patrol-car, GDB memtraces without RPC; SCRIPT-47, VEH-19)

Replica: `characterControl` (`src/runtime/director_hold.*`), `DirectorCamera::holdsControl`, `ScriptRunner::playerControlTaken`, `AiCore::setUpdateGate`; tests `director-hold`, `game-director-hold`, `game-director-release`, `game-options`.

**The test is a pointer compare in the per-update character routine.** 0x1835d0 (the character class update, run for every character entity) compares `*0x37689c` (a current-camera slot) with `*0x3768c4` (the director camera object 0x3768e8, the same global D+8 that the busy test 0x236104 compares) and builds a 5-word callback table `{control, 0x26be74, 0x285b38, 0x285b34, 0x1ccf2c}`; 0x26a19c then calls word 0 with the entity. Word 0 is **0x26be04 normally and 0x29bf30 while the director camera is current**. The siblings 0x190174 (0x29bf30 against 0x277980, which is 0x26be04 without the global byte test) and 0x1571dc / 0x158134 (0x29cd9c against 0x26d934; big routines on the vehicle component +0x2a4, not read) use the same pair test.
- 0x26be04: zero the controller halfwords +6 (heading), +0xc (held), +0xe (press); return when the signed byte `[0x375ee4 + 4]` (0x246128) is nonzero; if the entity is `*0x3772b8` (the player) and bit 4 of +0xd8 is clear: store 0.0 to ctrl+0x4c and run 0x200354 (the pad reader, [player-entity-input.md](player-entity-input.md#ts-20261013-105911)); otherwise run 0x200c30 (the AI controller: it works only when the entity flag +0xc bit 4 is clear and ctrl+0x14 equals +0x15, calls the state routine from the table `*0x3771f0` and ors press into held).
- 0x29bf30: the same three zeroings; if the entity is `*0x3772c0` and bit 4 of +0xd8 is clear it returns (no pad, no AI); else it runs 0x200c30 only when **bit 1 of +0xd9** is set, otherwise it returns.
- Bit 4 of +0xd8 is the AIEnable bit (and AIMove sets it, 0x17aefc; 0x17b054 and the AI end clear it) and bit 1 of +0xd9 is the DCamActive flag (0x1a2e48). So while a director camera is current: **the player not under AI control has held, press and heading zero** (stick and buttons do nothing, DCamActive does not free him); **a character under AI control, the player included, runs its AI only with DCamActive 1**; every other character does nothing. All 7 `DCamActive Player1 1` calls of lvl_01 sit next to `AIEnable Player1 1` and an AIMove (for example `Police_ExtToInt`: `AIEnable Player1 1; DCamActive Player1 1; PositionObject; StartDCam ...; AIMove Player1 ...`). The hold lasts exactly as long as `*0x37689c` is the director camera; it needs no other state.

**When the pointer changes and when the characters see it (oracle, `tools/oracle/dcam-hold-car.txt` and `ctrace` of 0x189548, 0x196784, 0x1835d0, 0x26be04 and 0x29bf30, state m11-2-patrol-car, dt 0.033).** Start: 0x189548 calls 0x226a30(D+8), which stores to `0x376870 + 0x28` = 0x376898, and sets D+0x24 bit 0. End: the end test 0x196784 clears D bit 0 and stores the default camera (0x377110) to 0x376898. `*0x37689c`, the slot the characters read, copies 0x376898 once per update **after the script runner and before the end test**. Order inside the update of the start (ctrace frame 101): 0x189548 (called by the script runner), then four character updates still with 0x26be04, then the end test; the next update (102) runs 0x29bf30 in all four. At the end, the last end-test call that cleared the camera is in frame 374; frame 375 still runs 0x29bf30 in all four characters, frame 376 runs 0x26be04. The end test is not called in the frames after the end (none in 375 to 380). So the characters are held from the update after StartDCam to the update after the end test.

**Oracle (`tools/oracle/dcam-hold-car.txt`, same state).** The player walks to `1-1_Waypoint_02` (record +0x311 of the police car goes from 3 to 1: unlocked), then X. Frame numbers are the stepped updates of the run (memtrace sample N is read after update N-1): X held at samples 76 and 77 (controller held 0x100, press 0x100 in the first); state 0x11a (jump in) from 76, 0x11c (Drive) at sample 99 (Drive began in update 98, 22 updates after the press, as in [vehicles-boarding.md §2026-10-15T08:15:49](vehicles-boarding.md#ts-20261015-081549)); at sample **102** both slots 0x376898 and 0x37689c read 0x3768e8 and D+0x24 = 5, so the first StartDCam of `1-1_Release_Car_Script` ran in update 101, 3 updates after Drive began; X pulses of 2 updates every 8 updates from sample 118: **held and press stay 0** for every pulse while the slot is the director camera; at sample **375**: `*0x376898` = 0x377110, `*0x37689c` still 0x3768e8, D+0x24 = 4; at 376 both 0x377110; the first pulse after that (sample 378) is read (held 0x100, state 0x11b: the jump out starts). The characters were held in updates 102 to 375 (274 updates, 9.0 s) and free from update 376, 278 updates after Drive began in update 98. Port: `DirectorCamera::holdsControl` copies the camera state at the start of its update (after the scripts, before the end test), so it holds from the update after the start to the update after the end test; `game-director-hold` and `game-director-release` (chase-game, the same story step with `1-1_VanBreakdown` and `1-1_Get_Car`): Drive begins at update 745, X at 763 and 1022 does nothing, X at 1023 (278 updates after Drive began) lets the player out.

**The clock.** 0x189548 calls 0x244970(`*(D+0x1c)`, 1) and the end test 0x244970(…, 0): a pausable stopwatch object (flag at +5, kind at +4, accumulated interval at +0x10; the clock read is 0x25cfc8) that is paused while the director camera is active and resumes with the paused interval added. `*(D+0x1c)` = 0x5165f0 in the oracle (scheduler C 0x5163e8 + 0x208). After the pause call the start runs 0x1a3d84 (stores 0 to floats and words of 0x376854 + 4 / +8 / +0xc) and then, if `[D+0xc]` (0x3768c8) is nonzero, jumps to it; the end test calls `[D+0x10]` (0x3768cc) after the resume when it is nonzero. Both words are 0 in the oracle (state m11-2-patrol-car before and after). Who sets them is not read.

**Other readers of the camera pointers and the busy test.** `*0x37689c` / `*0x376898` against D+8 are also read by 0x20ac88 and 0x235358 (both are predicates that are false while the director camera is current, while 0x246128 is nonzero, while the player is in a vehicle (0x24255c), while byte 0x375ef0 is set or ctrl+0xe0+0x130 bit 2 is set, and unless the player's state is one of 0..4, 32, 115, 120..125; 0x235358 has a second argument; their purpose is not read), 0x27c298 (the camera test only was read), 0x17e478 / 0x1b3724 (the words around 0x56d550: float +0 and byte +8 bits 1 and 2 are cleared there, StartDCamTrack sets the bits, the reader is not read) and 0x245258. The busy test 0x236104 has 33 call sites: the script waits (0x1663f8, 0x16642c, 0x166e08, 0x1883ec WaitForDCam), the HUD update 0x2d9f84 (twice: with the busy test true its button block at 0x2da018 / 0x2da194 is skipped), 0x171398, 0x17b678 (twice), 0x180168, 0x187b70, 0x193478, 0x1a1b44, 0x1d9094, 0x1ee4f4, 0x1ee848, 0x1ffaac, 0x200234 (the player update: with the busy test true the result of its event 19 is dropped, so 0x2b6c2c gets no target), 0x204fe0, 0x20ad70, 0x219614, 0x27b3e4, 0x27bb9c, 0x282edc, 0x28f8b0, 0x2a2cc0, 0x2a5f80, 0x2b9cf8 (room streaming, [streaming-rooms.md](streaming-rooms.md#ts-20261014-140018)), 0x2c2a10, 0x2d9f84, 0x2ddd64, 0x2e5158 and 0x313c3c. None of these except the character routines, the stopwatch and 0x200234 was read.
