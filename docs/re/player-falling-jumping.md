**Rules (confirmed by traces and code)**
- **Falling is the no-ground branch of 0x20b48c** (ev_7846beae…3319, decompiled earlier, re-read): when the box probe (0x22f134 through 0x1f9884) finds no floor it calls 0x203b34 (a long-reach ground query that fills ctrl+0x1e4/+0x1ec/+0x244, ev_7bfab5c8…ec49), then the event 0x26 through 0x244fc8, and if the handler accepts: `node.y -= ctrl+0x2b8; ctrl+0x2b4 += ctrl+0x2b8` (0x20b48c, last block). ctrl+0x2b8 is the fall speed in world units per update, positive downwards; ctrl+0x2b4 is the accumulated fall distance.
- **0x244fc8** dispatches to `table[entity+0x12 (type byte 27 for the player)]`: the table at 0x583138 has 0x28-byte entries; the entry for type 27 (0x583570) holds 0x18e4c8, the entity event function (read through RPC). Event 0x24 goes to 0x2b24bc (ground contact), event 0x25 to a state change to state 5 (fall).
- **Gravity step (event 0x26 handler, 0x18f1dc..0x18f238, objdump).** `g = 0x21df6c(entity, ctrl)` = `(1.0 - ctrl+0x9c) * *0x3771ac` (0x21df6c at 0x21df6c..0x21dfc4; `*0x377460` replaces the global when ctrl+0x317 bit 3 is set; type scaling for entity types 0x80..0x87 and 0x84..0x86 through 0x2cac54); ctrl+0x9c is 0 for the player and *0x3771ac = 0.05 (RPC read of 0x3771a4: 0.8, 0.1, 0.05, 0.8). Then `2b8 += g * 30.0 * dt` (literal 30.0 at 0x18f5a0; dt from 0x23602c), then `2b8 = min(0x2b75d0(), 2b8)` where 0x2b75d0 returns `*0x3771b0 = 0.8` (times 0x2cd758 for the same types). So at dt 0.033 the speed grows by 0.0495 per update up to 0.8 per update (at the 17th update); the position change per update is the speed itself (not multiplied by dt). Measured: run-off at dt 0.033 gives dy = 0.0495, 0.099, 0.1485, ... 0.792, 0.8, 0.8; dt 0.066 gives increments of 0.099, dt 0.0163 (requested 0.0165) increments of 0.0245.
- **Probe distance in the air (0x20b48c prologue).** The grounded call passes the distance of 0x20cd30 (`max(|movement| * sqrt(1 - 0.6088^2) - 0.1, 0.05)`, unchanged); the airborne call (0x20d3f8..0x20d418, flags 0x10) passes 0 and 0x20b48c replaces it with `max(|ctrl+0x2b8|, 0x21df6c)`: the box is swept from the node down to `y - 0.1 - distance`. Landing happens in the first update whose probe reaches a floor, so a fast fall reaches further down (terminal speed 0.8: 0.9 below the node). Fit: all 536 recorded updates of the test, height error at most 1.7e-5, fall speed error at most 5e-7, no wrong decision.
- **A standing character is not probed** (ctrl+0x314 bit 6 set and no movement, 0x20d500 area): a player teleported into the air with the stick at rest stays there (trace `float_still`, 8 updates at y 25, state 1). The fall starts with the first movement.
- **Horizontal motion in the air** is the locomotion of the stick, unchanged: run 0.2277 per update at dt 0.033 (6.9 u/s) in every airborne row (`fall_tall_run`), walk 0.0759 (2.3 u/s) with the stick in the walk range, zero as soon as the stick is released in the air (`fall_release_*`), the facing keeps turning toward the intent. The run timer (ctrl+0x24c) is 0 in the air and the scale ctrl+0x94 stays 1.0.
- **Landing (event 0x24, 0x2b24bc tail, ev_45be726f…3a63c14).** The update in which the probe finds ground sets the node to the ground height (the usual 0.01 keep rule), clears 2b8 and 2b4, and decides the next state from the fall distance before the reset: `2b4 >= *0x374360 (12.0)` is a **hard landing** (state 7, also when the stick is held; measured: fall 12.51 m hard, 11.51 m soft); otherwise, if the held flag bit 0 (stick active) is set the state goes straight to run or walk (state 2 / 3 by held bit 3) and no stun happens (platform trace: landing row has state 2 and movement); if no stick is held and `2b4 <= 0.05` the state is idle (1), else a **soft landing** (state 6). **Which button (confirmed).** B (3DS B, slot 7 = 0x376a04 = channel 17) jumps; the keyboard key for B is Q in config/controls.cfg (right mouse button too). Code: the controller 0x200354 maps slot 6 (A, 0x376a00) to `ctrl+0xc |= 0x84` and a press edge to `ctrl+0xe |= 4` (event 7, 0x200928: `mov r2,#7 ... bl 0x21e1d4`), slot 7 (B) to `ctrl+0xc |= 2` and `ctrl+0xe |= 2` (event 6, 0x200948). Oracle: a tap or a 12-update hold of A in state 1 changes nothing (event 7 had no visible effect; ctrl+0xc bit 7 appears only after 9 held updates); a B press (ctrl+0xe = 2) switches ctrl+0x6c (state) from 1/2/3 to 4 in the same update. Holding B for 70 updates does not repeat the jump, and a second B press during the rise (update 8) or the fall (update 16) does nothing (no double jump for this character, although tablesanimations has a "jump_double" row 215 for another class).

**Height (fit, exact to 4e-4).** The jump is animation root motion. The animations class_police/jump_minifig.bfnanm (standing) and jump_run_minifig.bfnanm (stick active at the press, also walking) each carry a sub-animation (index 1) with the tracks 0xdcd633e0, 0xdcd633e1, 0xdcd633e2 (root x, y, z; the walk/run/sprint animations have only constant zeros there, which is why no speed could be derived for them). The y track (0xdcd633e1, 6 Bezier keys, peak 2.43 / 2.53) reproduces the node height of every airborne update:
- `y(n) = y_takeoff + k * lerp(T(f / 11), T((f + 1) / 11), p - f)`, `p = n * dt * 15`, `f = floor(p)`, T = the track at normalised time (chase_assets `evaluateTrack`), n = number of updates since the press update (n = 0 is the press update, in which the height does not change), capped at p = 11. So the track is sampled at 15 frames per second over the 12 animation frames (11 intervals, duration 11/15 = 0.7333 s) and interpolated linearly between frames. Rise per update at dt 0.033: 0.2703, 0.2703, 0.2771, 0.2773, 0.2445, 0.2432, ... (consecutive pairs are nearly equal because a frame spans two updates). Verified at dt 0.033, 0.066 and 0.0165: the profile is a function of elapsed time.
- `k` = 0.860869 for jump (standing), 0.828197 for jump_run (walk, run, sprint alike; the sprint scale 1.5 does not change the jump). Both give the same apex: `k * peak` = 2.094 (jump) and 2.093 (jump_run), i.e. the animation is scaled to a jump height of about 2.09 units above the take-off (entity+0x5c = 1.16314; 1.8 * 1.16314 = 2.0937; the source of k was not traced). k is PROVISIONAL (fitted). The residual of the fit is a smooth pattern of at most 3.7e-4 (probably the original's own Bezier evaluation; not pursued).
- The rise ends at the apex 18.68 (take-off 16.589: 2.09), then the same track descends; at p = 11 the track is back at -0.007 * k. The y change per update is the root delta of the animation (0x20d1b4 stores `2b8 = -dy`, 0x2c9770 adds the root delta to the movement vector, 0x20d298 adds it to the node).

**Ground probe during the jump.** Rising updates (dy > 0) find no ground in the data (street far below). On the way down the grounded call of 0x20b48c with the 3D movement length finds the street: the landing update is the first update whose probe box (`max(|move| * sqrt(1 - 0.6088^2) - 0.1, 0.05)` below the new node height) reaches the floor; the unsnapped height is below the floor and the node is set to the bisected floor height. A variant with the airborne distance `max(|dy|, 0.05)` lands one update too early. Landing heights agree within the bisection resolution (errors of 1.2, 4.1, 6.4, 6.3, 0.8 and 8.4 mm; the test allows 1e-2); airborne heights agree within 3.7e-4.

**Forward motion.** The stick keeps steering during the whole jump, also after a standing take-off and when released or turned in the air (jstick, jrel, jturn): the horizontal speed is **0.8 times** the ground speed of the regime: walk 0.0608 (0.8 * 0.0759), run 0.1822 (0.8 * 0.2277), sprint 0.2732 (0.8 * 0.3415) per update at dt 0.033, 105 airborne updates checked. The factor equals ctrl+0xa0 (0.8, read in the controller dump; 0x3771a4 also holds 0.8); that it comes from there was not traced. The facing turns by the usual 0.3 / 6400 step. The press update itself moves at the full ground speed. While jumping the run timer (ctrl+0x24c) keeps its value and a sprint stays active (ctrl+0x94 = 1.5); at the landing update with the stick held in the run regime the timer restarts at `(sprint ? 1.0 : 0) + dt` (0.03 after a run jump, 1.03 after a sprint jump, which keeps the sprint speed at once). Falls restart at 0 + dt.

**Landing.** The same rule as the fall landing: stick held (ctrl+0xc bit 0) goes straight to state 2 / 3 without a stun; stick released lands in state 6 (soft landing) for 26/30 s (27 updates at dt 0.033, 14 at 0.066, 54 at 0.0163, measured on jump landings too), then one idle update (state 1). ctrl+0x2b4 during the descent holds twice the current descent step (not a sum), so a jump never counts as a hard landing.
