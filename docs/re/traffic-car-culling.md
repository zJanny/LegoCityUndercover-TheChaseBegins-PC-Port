# Traffic: the culling bit of a car's node

Subtopic of [traffic.md](traffic.md); the keep counter that reads the bit is in [traffic-ai-driver.md §2026-10-25T12:26:09](traffic-ai-driver.md#ts-20261025-122609) (post step 0x1bc79c, `pedestrianNodeHidden` 0x23de70) and [pedestrians.md](pedestrians.md). This file: who sets bit 18 (0x40000) of a mesh node's word, and what the port sets. The brake light glow that reads it is in [traffic-car-lights.md](traffic-car-lights.md).

## Current state

- The only writers of node word bit 18 are in the scene walk 0x20eb58(node, matrix): it clears the bit, calls the visibility function of the node's type (table 0x5303c4, row `word & 31`, slot +4) and sets the bit when that returns 2. A node whose word has bit 5 or bit 7 (0x20, 0x80) is left as it is. The walk goes on to the children unless the node's word has bit 6, and stops below a culled node whose word has bit 17. The caller is the scene walk 0x228d40 of a render pass (tail call from the root of the node tree), which first sets the camera record 0x529e30 and builds the view volume of the list 0. [§2026-11-12T00:12:13](#ts-20261112-001213)
- The mesh node type (2) registers 0x2072ec as its visibility function. It returns 2 when the fade byte +0xdd or the node alpha +0x11b is 0, or when the bounds test 0x10e628 finds the node's sphere (+0xa0 centre, +0x9c radius; flag 0x200, node word bit 14) outside the view volume, or when every part of the mesh is culled one by one (0x10e028); it returns 0 for a node whose LOD resource is not a mesh. A node with a palette (+0x110) loses the sphere and box flags (0x800 stands in). [§2026-11-12T00:12:13](#ts-20261112-001213)
- The view volume of the list 0 (kind mask 15; a mesh node tests with mask 3, or 19 for a shadow caster, and only list 0 has a frustum) is six planes built by 0x224194 from the camera record: left, right, bottom, top, near and far, all in the camera's frame (rows 0..2 of the record the screen right, up and view direction, +0x30 the position). A point outside has a x + b y + c z + d above the sphere radius. The camera constructor 0x258744 gives +0xbc = 1.2, +0xc0 = 1.2 x 400 / 240 = 2.0, +0xcc = +0xd0 = 0. ## 2026-11-12T00:12:13+01:00 — Who sets the culling bit 18 of a node, and the view volume it tests (llvm-objdump only, no REA session, no emulator)

[Corrects traffic-driver-connect.md §2026-11-08T12:18:49](traffic-driver-connect.md#ts-20261108-121849): the keep counter no longer takes the node as always hidden (TRAFFIC-S7); the port sets the culling bit from the camera's view volume (TRAFFIC-S35).

Method: `llvm-objdump -d --triple=armv6k-none-eabi --mattr=+vfp2` on `artifacts/game/game.arm.elf` (worker 20261111-chase-G, 2026-11-11), read at 0x20eb58..0x20ec7c (walk), 0x228d40..0x228de0 (render pass walk), 0x2072ec..0x2075d0 (mesh visibility), 0x10e628..0x10e6c0 (bounds test), 0x24f184..0x24f29c (sphere against the volume), 0x224194..0x2243e4 (planes), 0x258744..0x2587c0 (camera constructor), 0x105bc4..0x105cac (draw list set-up), 0x258eb0 and the five node type registrations (0x103194, 0x103268, 0x1032c4, 0x105ba4, 0x1ed54c). Every store of `orr #0x40000` to a node word was searched in the whole disassembly: the only one that reaches a node is 0x20ebf4. Port: `src/runtime/node_view_cull.*`.

**The writers.** `orr x, x, #0x40000` appears at 0x12fb8c, 0x15a93c, 0x225b74 and 0x2e4b5c with other bases and at 0x20ebf4; the last one is the node walk. 0x20eb58(node, matrix) (matrix 0 gives the node's world matrix 0x250810): word bits (word << 7) >> 12 & 5 non-zero skip everything below; otherwise bit 18 is cleared, the type's function (row `word & 31` of the 16-byte table 0x5303c4, +4) is called with (node, matrix, 0, 0), and its result decides: 2 sets bit 18 (and counts it in 0x529d80 +0x28; when the word has bit 17 the children are not walked), 1 and 0 only count. Then, unless the node's word has bit 6, each child (+8 first, +0xc next) is walked, with the parent's matrix when the child's word has bit 10, else with 0.

**The node types.** 0x258eb0 takes a slot of the table 0x5303c4 (slot 0 is reserved by 0x10332c) for each registration record {+4 visibility, +8, +0xc handler}: 0x105b78 registers {0, 0, 0}, 0x103290 the mesh node type (0x2072ec, 0x106858, 0x106980), 0x103238 {0, 0x106810, 0x106818}, 0x103160 {0x105cd8, 0x1066dc, 0x106708}. The mesh node type is 2 ([pedestrians-fade.md §2026-10-20T14:12:57](pedestrians-fade.md#ts-20261020-141257)), the traffic cars' node word 0x4202 ([traffic.md](traffic.md)) is that type with bit 9 and bit 14 set.

**The mesh visibility function 0x2072ec(node, matrix).** It picks the LOD resource (0x10da18(node, camera position)) and returns 0 unless it is a mesh (byte +8 = 2) with mesh data (+0x14); then 0x10eb70 (the fade step, [pedestrians-fade.md](pedestrians-fade.md)). It returns 2 when the byte +0xdd or +0x11b is 0. The flags r7 = (word << 7) >> 12; a node with a palette (+0x110 not 0), or one whose +0xc8 record has the low nibble of its first byte equal to *0x376758 and passes 0x10e5cc, has flags that held 0x100 or 0x200 replaced by 0x800. 0x10e628(flags, node, matrix) returns 1 (culled) when flag 0x200 is set and the sphere test 0x24f184(matrix, node +0xa0, +0x9c, mask) fails, or when flag 0x100 is set and the box test 0x24f05c fails; the mask is 3, or 19 for a node of the mesh type whose +0xde has bit 0 (shadow caster). After the bounds the function tests each node of the mesh's node table (skipping the hidden bits of +0x114, [traffic-car-lights.md](traffic-car-lights.md)) with 0x10e028 against the volume counting a hidden or culled node, and returns 2 when all counted nodes are the whole table (a node without a mesh is not counted, so it keeps the result at 1), else 1.

**The volume test 0x24f184(matrix, centre, radius, mask).** The centre goes through the node's matrix rows (row vectors, VFP vector mode of length 3: c.x row 0 + c.y row 1 + c.z row 2 + row 3). For each list of the table 0x530634 (count 0x3767f0, stride 0x20) whose kind word has a bit of the mask, the world point minus the camera record's position (+0x30) is rotated into the camera's frame by the rows 0..2 of the record (x' = row 0 . d, y' = row 1 . d, z' = row 2 . d), and each of the plane records {a, b, c, d} of the list's volume (+0x18, count first, +0x1c the camera record) must give (a x' + b y') + (c z' + d) not above the radius; the first list that passes gives "visible". Only list 0 (kind mask 15, set up by 0x105bc4 with the volume 0x52a150 and the camera record 0x529e30) has a volume.

**The planes 0x224194(camera, planes).** A camera whose byte +0xb8 is 1 gets the orthographic set (not read); the others six planes from the scales a = +0xbc, b = +0xc0, the shifts c0 = +0xcc, d0 = +0xd0, near +0xc4 and far +0xc8, with k = 1 / sqrt(s^2 + scale^2) for s the offset below:
- left (-a k, 0, s k, 0) with s = -1 - c0, right (a k, 0, -s k, 0) with s = 1 - c0;
- bottom (0, -b k, s k, 0) with s = -1 - d0, top (0, b k, -s k, 0) with s = 1 - d0;
- near (0, 0, -1, -near) and far (0, 0, 1, -far).
In the frame of the record the view direction is row 2 and +z is forward (the left plane is outside for a x' < -z' / a). The camera constructor 0x258744 stores +0xbc = 0x3f99999a (1.2), +0xc0 = 1.2 x [0x529e30 + 0x10c] / [0x529e30 + 0x110] (2.0 for 400 x 240), +0xcc = +0xd0 = 0, +0xb8 = 0.

**Where the walk runs.** 0x228d40(camera, ...) stores the camera as 0x529e30 +0x2c, builds the frame 0x227300 and the planes, sets the view (0x24a554, 0x25a55c) and walks the node tree from its root. It has ten callers (0x17cbac, 0x193670, 0x1dd15c, 0x262050, 0x27af2c, 0x29054c, 0x2d57bc, 0x2d5800, 0x2d8914, 0x2ddb38), among them pass 1 of the frame 0x2e4858 ([rendering-draw-order.md §2026-10-27T18:49:04](rendering-draw-order.md#ts-20261027-184904)). Every call recomputes the bit of the whole tree, so the bit a car update reads is the one of the last walk of the previous frame.

**What the port sets (TRAFFIC-S35).** After each draw of the top view `LevelSession::cullTrafficCars` gives every live traffic car the bit `viewNodeCulled` computes with the view the draw used: the camera record from the view matrix (position, right, up and forward rows), the scales from the vertical field of view and the aspect of the original's 400/240 view region (not the drawn view's) (tan(fov / 2) = 1 / b, a = b / aspect, which reproduces 0x258744's 1.2 / 2.0 for tan(fov / 2) = 0.5 at 400 x 240), the near and far plane of the draw, the car's matrix, the centre and half diagonal of the model's bounds as the sphere, the fade byte of the manager. The post step reads that bit for the keep counter and the brake lights; before the first draw the bit is clear.

**Stand-ins (TRAFFIC-S35).**
- the sphere is the model's bounds (`assets::modelBounds`, radius = length of the half extents) as for the pedestrians (PED-S11), not the node's own +0x9c / +0xa0 (the record source of 0x10d2d4 was not read);
- the per-node tests 0x10e028 against the volume, the palette flags and the box test are not ported: a node whose sphere is inside is not culled;
- the camera record fields +0xbc / +0xc0 are derived from the projection (the camera manager's writers 0x25bf18 and 0x25bf44 were not read), and the 3D mode's second eye is not modelled;
- the parent test of 0x23de70 (a parent with both bits 17 and 18) is not applied, and the port's draw is the only walk (the other callers of 0x228d40 may leave a different bit).

Unknowns:
- Which walk is the last of a frame for a gameplay car (the shadow camera, reflections and other screens call 0x228d40 too) and whether it uses the main camera's volume.
- The records of 0x10d2d4 that give a mesh node's +0x9c / +0xa0, and the per-node test 0x10e028.
- The writers of the camera record's +0xbc / +0xc0 in a follow camera and a cutscene camera (the field of view) and how the 3D mode changes the volume (mask bit 1, shifts).
- The orthographic planes of 0x224194.
