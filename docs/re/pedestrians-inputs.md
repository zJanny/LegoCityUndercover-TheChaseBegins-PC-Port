# Pedestrians: the vehicle test and the state the manager reads

Subtopic of [pedestrians.md](pedestrians.md): the pedestrian's vehicle test 0x1ffcd4 and its list, and the sources of the state the pedestrian manager 0x51b33c reads from the rest of the game (the room layer table, the class byte, the room node +0x7c, the mesh node type, the distance fade record), the second update caller and the scene that sets the limit. Items: [pedestrians-traffic-pedestrians.md](../plans/features/pedestrians-traffic-pedestrians.md).

## Current state

- 0x1ffcd4 tests a pedestrian against one vehicle box. With |speed x dt| at most 0.1 it returns 4 when the target lies past the vehicle and slides the step off the faces it crosses. Faster, it requests a dodge (3 or 4, after a ray to that side) or a splat (6), and returns 3 or 0. The spawn (0x26cd38) and the walk (inline loop 0x2b9340) run it over the vehicle list 0x5863b4 + 0x305c, skipping kinematic bodies. [§2026-10-20T13:20:02](#ts-20261020-132002)
- The room layer table *0x376ad4 is a stack. The game set-up fills it (0x1590b0, then 0x2ed0b4 for class 6), each cutscene pushes a copy of the set-up table with class 6 cleared, and the cutscene end pops it. [§2026-10-20T13:20:02](#ts-20261020-132002)
- The pedestrian's class byte +0x18 is 0 from its create. Room +0x7c is the node that holds a room's faded-out mesh nodes. *0x37674c is 2 (slot 0 of the node type table is reserved first; [pedestrians-fade.md §2026-10-20T14:12:57](pedestrians-fade.md#ts-20261020-141257)). The fade record 0x376794 gives 3, 36 and 38, so the distance fade table is (3, 6, 12), (36, 72, 108), (38, 76, 114). [§2026-10-20T13:20:02](#ts-20261020-132002)
- The second update caller 0x164240 is the cutscene mode's update 0x2fae68. The last loaded world sets the slots and the limit. [§2026-10-20T13:20:02](#ts-20261020-132002)
- Port: `src/runtime/pedestrian_blocked.*` (test `pedestrian-blocked`) and `src/runtime/room_layers.*` (test `room-layers`), not wired. [§2026-10-20T13:20:02](#ts-20261020-132002)
- A walking pedestrian is moved between rooms by the room pass 0x2e6ce4 like every other object (list 0 of its room, the player's room and the round-robin entry); its priority byte +0x19 is 128 from the object loader. Ported as `src/runtime/pedestrian_rooms.*`. [§2026-10-20T14:10:27](#ts-20261020-141027)
- The speed 0x34163c is the signed velocity along the vehicle body's forward axis; the bump reads the player controller state +0x6c (2 run, 3 walk). Ported with the port's `forwardSpeed` and `src/runtime/player_controller_state.*`. [§2026-10-20T14:10:27](#ts-20261020-141027)
- Open: the run-time values of a live pedestrian's byte +0x18 and the room byte +0x3a; the third table push 0x17e544; the level root's slot values. [§2026-10-20T13:20:02](#ts-20261020-132002)

**The vehicle test 0x1ffcd4(pedestrian, position, vector, vehicle e, dt).**
- Inputs: e's half extents x +0x6c and z +0x74, e's radius +0x5c, e's matrix 0x250810(e +0x3c), the speed 0x229948(e +0x84) = body +0x24 . rigid body +0x13c (0x24092c), the pedestrian's radius +0x5c and its component +0x7c (requested state hword +4, dodge side +0x5f, walk byte +0x62, target +0x38).
- limit x = half x + 0.9 (0x200048), limit z = half z + 1.8 (0x20004c), step = |speed x dt|, reach = limit z + 8.0 (0x200050) x step. next = position + vector. When the squared distance of next from e's translation (0x24ef70) is greater than (e radius + pedestrian radius + reach) squared, the result is 0. local = next in e's frame (0x2536c0: the dot products of next - translation with rows 0, 1, 2).
- The slow branch: step compared with 0.1 (0x200054) as signed integer bits, at most 0.1. Outside |local x| < limit x or |local z| < limit z the result is 0. The result is 4 when (translation - position) . (target - position) > 0, else 0. Then the vector slides: with now = position in e's frame, n = (row 0 x, 0, row 0 z), when now x > limit x and local x < limit x, 0x22f928(n, vector); else when now x < -limit x and local x > -limit x, the same with n's x and z negated. The same follows for z with (row 2 x, 0, row 2 z) and limit z. 0x22f928: d = n . v; when d < 0, v -= n x d (0x2408f8, 0x227790). The z check uses local z of the unslid next.
- The fast branch: outside |local x| < limit x the result is 0. With bit 0 of +0x62 and reach > |local z|, two sides are tried. Offsets (5.0, -5.0) with states (3, 4), or (-5.0, 5.0) with (4, 3) when local x < 0. The states are the table 0x357e1c {3, 4}, and 5.0 is *0x37449c. For each side the ray runs from = position with y + 0.25 (0x200064) to = from + row 0 x offset, with to y = from y. It uses 0x22b108 and the query {0x362298, 1, 16, -1, 0, 0, 0, 512, 3, 0, byte 1} on the stack. The first side without a hit sets +4 to its state and the result to 3. +0x5f becomes 1 for the second side. For the first side it is 0x235498(2) (next random word % 2) when reach > speed or the compare is unordered, else 1.
- After the fast branch, when +4 is still 2 and |local x| < half x and |local z| < half z, +4 becomes 6 and +0x62 becomes 0. The result stays as it was.
- The list: the physics step 0x2e2bc8 rebuilds it every step from the world's collision objects (+0x2c +0xe8, user pointer +0x108 = the vehicle body). It keeps the bodies with flags +0xc4 bit 0 whose entity (0x236174) has neither bit 0 nor bit 5 of +0x10. The entity goes to +0x305c and the body position +0x34 to +0x3124. 0x26cd38 and the walk's own copy of the loop (0x2b9340 .. 0x2b93a4, called with the node position, the step velocity and dt) skip an entity whose body's rigid body has bit 1 of +0xcc (Bullet's kinematic flag). They return the first non-zero result, else 0. The walk adds the vector after the loop (0x2b93c0), so a slide changes the step. The spawn passes a zero vector and 0.0, so it only takes the slow branch: 4 or 0, with no change to the pedestrian.

**The room layer table *0x376ad4.** It is a pointer to the current table, used as a stack. 0x1b3ebc(t) stores the old pointer in t +0 and makes t current. 0x1a4b9c makes the next table current and clears its link. Both also set byte +0x3a of every room of the loaded scenes to 255.
- Game set-up: 0x168de0 (at 0x2f5cf4) calls 0x1590b0. That clears the 276 bytes at 0x5859b0, makes it current and calls 0x2405a0(class, first type, bit 0, bit 1) as follows: for each class 0 .. 6 (0, 1, 1) and (16, 1, 0); class 0 (0, 1, 1) (16, 0, 0); class 1 (0, 1, 1) (16, 0, 1); class 2 (0, 0, 1) (16, 0, 0); class 3 (0, 0, 0); class 4 (0, 1, 0) (16, 0, 0); class 5 (0, 1, 1). Later 0x157a00 (at 0x2f5d08) registers the pickup system *0x377288 = 0x58ef1c (vtable 0x362778) through 0x163c34. 0x2411ac then calls its slot +8 0x2ed0b4, which sets class 6 (0, 1, 1) (16, 0, 0).
- Result, bit 1 (the room test 0x1ffbd8) per class for types 0 .. 15 / type 16 and up: class 0 1 / 0, class 1 1 / 1, class 2 1 / 0, class 3 0 / 0, class 4 0 / 0, class 5 1 / 1, class 6 1 / 0.
- Cutscenes: the start (0x196734) pushes 0x5898e0 and calls record 0x376d18 +0x14 = 0x16c060. That copies the 272 bytes of the set-up table (0x5859b4, not the current table) into it (0x25bc34) and sets class 6 (0, 0, 0). The cutscene mode's update 0x2fae68 pops it (0x2faf50) at the end. Class 6 is the pickups' class (0x2a2bc4 tests rooms with class 6).

**The class byte +0x18.** The object loader 0x1a4130 clears the 0x88-byte info record (0x2594d8 at 0x1a41e0) and writes +0x10, +0x12, +0x13, +0x19 and +0x1a, but not +0x18. The pedestrian create 0x1913f8 copies the record and does not write +0x18 either. So a pedestrian's class is 0 after its create. The other 101 `strb [rN, #0x18]` sites of the code were not checked for later writes. Traffic (0x2df098, 0x2e00f8) and 0x26ddac, 0x2cd5c4 pass entity +0x18 to 0x1ffbd8 too.

**Room +0x7c.** The per-update pass 0x2e6ce4 (the room pass of the main update, [streaming-rooms.md](streaming-rooms.md)) walks the entities of four lists per room (+0x58 + 8 n). It skips kinds 90, 179, 183 and 243, and runs only while byte 0x52a1cd is 0. A node of type *0x37674c with distance fade (+0xde bit 4) moves from under room +0x14 or +0x18 to under room +0x7c when its alpha byte +0xdd is 0 (0x245048, 0x245008, then 0x22d480). A node under room +0x7c goes back through 0x23c1a8 when the draw test 0x2930e0 passes. So room +0x7c holds the room's faded-out mesh nodes, and the manager removes a pedestrian whose node was parked there.

**The mesh node type *0x37674c.** No store goes through a pool word of 0x37674c. 0x103290 stores the result of the node type registration 0x258eb0 at 0x376744 +8 = 0x37674c. 0x258eb0 takes the first free 16-byte slot of the table 0x5303c4 (count [0x3767dc +4]), else the next number. The start-up 0x102100 (called at 0x100a04) registers 0x105b78 first (id 0) and 0x103290 second, then 0x103238 and 0x103160. No other call of 0x258eb0 is reachable from it before that. The fifth caller 0x1ed440 runs only from 0x217f74, 0x2e60d4 and 0x2fadcc. So *0x37674c = 1, read from the order. The static initialisers were not searched.

**The fade record 0x376794.** A static initialiser (0x3497a4 .. 0x3497bc) stores +0x1c = 36.0, +0x20 = 38.0 and +0x24 = 3.0. No other store reaches those words. 0x1077dc (from 0x25addc and 0x25c00c, only when 0x529e30 +0x3c8 is 0) writes radius (r, 2r, 4r) = (3, 6, 12), fade-in (f, 2f, 3f) = (36, 72, 108) and fade-out (38, 76, 114) (multipliers 2.0, 4.0 and 3.0 at 0x107900). Those are the port's `DistanceFadeTable` defaults, now from the code.

**The probe floats 0x374494.** The static initialiser 0x347904 stores 0x374494 = {0.25, 0.25, 5.0}. The walk's ground probe 0x2058cc reads the first two, and 0x1ffcd4 reads the third (the dodge offset).

**The second update caller.** 0x196328 (from 0x2f5d44) fills the record 0x376d18: +4 0x26b088, +8 0x164240, +0xc 0x2b1094, +0x10 0x1aa9a4, +0x14 0x16c060, +0x18 0x175c38 and +0x1c 0x5163e8. The cutscene mode's update 0x2fae68 (vtable 0x363134, [cutscenes.md](cutscenes.md)) calls +8 with dt each update (0x2fae88 .. 0x2fae94). So 0x164240 is the pedestrian update during a cutscene. It runs the manager update and the pedestrians of the current room's scene ([pedestrians.md §2026-10-20T12:27:05](pedestrians.md#ts-20261020-122705)), in place of the gameplay step.

**The scene that sets the limit.** The level load 0x2ee4c8 runs from 0x27ecb8, which is called at 0x1c3b34 in 0x1c39c4. 0x17f104 registers that function as the loader of the resource type "world" (0x258f1c). So it runs once for each world file that finishes loading. Each run sets the slot count to 0 first, so the last loaded world sets the slots and the limit. Each shipped level has one world, `<level>_main.blvl`.

**Port.** `pedestrianVehicleBlock` and `pedestrianBlocked` take the vehicles as `PedestrianBlockVehicle` (matrix, half extents, radius, speed, kinematic) and the line test 0x22b108 as a callback. `startupRoomLayers`, `cutsceneRoomLayers` and `setRoomLayers` give the table. Nothing is wired. `PedestrianWalkWorld::blocked` takes the velocity as const, so the walk cannot take the slide yet.

**Room move of a walking pedestrian (PED-11).**
- Pass 0x2e6ce4 handles per update the player's room and one round-robin entry of the current room's list ([streaming-rooms.md §2026-10-14T20:51:26](streaming-rooms.md#ts-20261014-205126)). Per room it walks the lists at room +0x58 + 8 n for n = 0, 1 and 2 (the loop stops when n reaches 3, 0x2e6dac), through the next pointer at entity +0. It skips the kinds 90, 179, 183 and 243.
- Only list 0 is room-tested (0x2e6ec0: n must be 0). The entity needs hword +0x10 bit 2 clear (0x2e6ecc), the node word (node = entity +0x3c) bit 19 set (0x80000), entity bit 10 clear and the node's parent (node +4) equal to room +0x14. The test point is the node translation plus the node's local box centre +0xa0 (0x23f50c); 0x1fa5d4 (point lifted by 0.1 inside the room box) keeps the room. Otherwise 0x237b04 picks the room, and the final loop re-parents the node to the new room +0x14 (0x245048, 0x245008), sends message 0x51 to the entity (0x244fc8) and re-buckets it (0x242b08).
- 0x242b08 buckets an entity by its own flags: the list at room +0x70 when hword +0x10 bit 0 is set, else list +0x58 + 8 x byte +0x13. The disable 0x2428c0 sets bit 0 of +0x10 (and re-buckets), so a disabled slot is in the disabled list and an enabled one in the list of its byte +0x13. The create 0x1913f8 stores 0 at +0x13 (0x191434). So an enabled pedestrian is in list 0 and is moved like any other object: it follows its walk into the room that contains its box centre. The port runs this for every enabled pedestrian with the player's room and the round-robin entry (the same `ObjectRoomMover` rule as the vehicles).
- In a run of lvl_01 from the start (`--no-start-cutscenes --script "0 0 300"`, with the mesh node tier 0 spawn window) slot 5 changes from Room8 to Room7 at update 281 (the port's own run, not an oracle value and not measured in the original; the test `game-pedestrian-rooms` pins it).

**The priority byte +0x19.** The object loader 0x1a4130 writes 128 (0x80) at +0x19 of the 0x88-byte record (strb at 0x1a4214, record base sp + 8), and the create 0x1913f8 copies the record and stores no other value, so a pedestrian's priority is 128. It is the sort key of the entity pass ([scripts-runtime.md §2026-10-20T09:22:38](scripts-runtime.md#ts-20261020-092238)); the port updates the pedestrians in the object phase instead (PED-S7).

**The speed 0x34163c(body = vehicle +0x84).** It copies body +0x24 .. +0x30 (a direction, the body's forward row) and reads the rigid body's linear velocity ([body +0x7c] +0x13c), then returns their dot product (0x257e78). 0x229948 is the same dot product by way of 0x24092c, so 0x34163c is the signed velocity along the body's forward axis, as the port's `forwardSpeed` has it. It is not the length of the velocity: the spawn's view moves ahead only while this speed is above 0 (0x2ee0d4), so a car that reverses does not move it.

**The player state +0x6c in the bump (0x1fd8c8).** It reads the halfword at +0x6c of the component [player +0x7c] (0x1fd938 .. 0x1fd944) and bumps for 2 or 3. That halfword is the controller state ([player-falling-jumping.md](player-falling-jumping.md): 1 idle, 2 run, 3 walk, 4 jump, 5 fall, 6 / 7 landing, 8 slide), which [player-entity-input.md](player-entity-input.md) calls the entity type. The port derives it from the posture and the playing locomotion role (PED-S14).
