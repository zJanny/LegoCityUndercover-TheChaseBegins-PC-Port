# Gameplay camera

How the original game places the gameplay camera and where the yaw word 0x376894 comes from. Findings from REA (Ghidra 12.1.2, `artifacts/game/game.arm.elf`) and the Azahar oracle (`gameplay-start` checkpoint, Chase in the street of lvl_01).

### Writer of 0x376894 (corrects "writer not found", player.md and the 22 readers)

- 0x23f174 (camera manager update, struct at 0x376870) ends with `DAT_00376894 = atan2f(row2.x, row2.z)` of the **camera scene node's world matrix** (node 0x3768b4; row 2 = node+0x7c / +0x84, the forward axis), or 0 when both are zero (store at 0x23f410; `vstreq s16` at 0x23f400 for the zero case). It is therefore the yaw of the view direction in radians, forward = (sin yaw, cos yaw).
- The oracle watchpoint on the word stopped at 0x23f420 right after the call to 0x23c188, in this function, in the frame with the stick pushed. The recorded yaw equals atan2(look.x − eye.x, look.z − eye.z) of the pose on every row of all traces (exact to float precision).
- The player controller 0x26be04 adds `(s16)(yaw * 10430.378)` to the stick heading, so it reads the value of the previous camera update (the manager update runs after the controller in a frame). player.md already records that order.

### Manager and modes (0x376870)

- Manager fields: +0x14 camera object C (pointer at 0x376884), +0x18 optional post callback (0x376888, 0x1c607c shake in the oracle), +0x24 the yaw word, +0x28 requested mode, +0x2c current mode, 0x3768b4 / 0x3768b8 camera scene nodes (two eyes), 0x3768a8 aspect 5/3 (400/240), 0x3768ac 4.0.
- A mode is a table of function pointers, word 6 = active flag. The gameplay mode is the static object 0x377110: enter 0x1984e8, leave 0x1984e4, update 0x1b4a30 (record selection and blend set-up, see data-tables-config.md), 0x217b04, pose step 0x181fe0. 0x226a30 sets the requested mode (about 18 callers: other modes exist).
- Per frame: mode update, then `FUN_001cf0b8(C)`, which advances filters, evaluates the pose into C+0x10 and runs the registered controllers (a blend controller or the follow controller, below), then C+0x4c = pose after the "Filters" smoothing, then the mode pose step 0x181fe0 (0x2821f8 adds a shift that decays to zero unless a record has Type bit 0x100 or 0x200; see corrections), then the matrix and projection.
- Pose layout at C+0x4c (and C+0x10): look point (+0x00..), roll (+0x0c), flags (+0x10, bit 0x40000000 = no rotation), eye (+0x24..+0x2c), FOV in degrees (+0x30), shake and 3D offset (+0x34, +0x38). Matrix 0x2ca814 -> 0x22859c: row 2 = normalize(look − eye) (forward), row 0 = (fz, 0, −fx) normalised (right; for |fy| >= 0.98 it is (0, −fz, fy)), row 1 = row2 × row0, translation = eye. 0x24c118 stores it as the camera node's world matrix.
- Projection 0x23458c(fovRad, aspect, node): f = cot(fov / 2); y scale = f * 4/3, x scale = y scale / aspect. With the pose FOV 40 this is a vertical field of view of 2 atan(0.75 tan 20°) = 30.5°. Checked against gameplay-start.png: the character takes 35 % of the height in the original and 36 % in chase-game with it (27 % with a plain 40° vertical FOV).

### Which controller runs in the street

- 0x19b8c8 (new record set) hands over to **0x1b4864** when exactly one record is active, it is a Room (+0x4e) and DAT_003770c8 == 0. That is the case at gameplay-start. 0x1b4864 registers the controller **0x2a8bfc**, which calls the follow camera update 0x2e0bf0 on the camera system object `K` at 0x589a70 and copies its result into the pose: eye = K+0x34, look = K+0x94 + K+0xf4. Pose FOV in C+0x7c was 40.0 and the roll 0.
- The other path (several Room/Bound records, or DAT_003770c8 != 0) is the record pose blend 0x298cd8 of data-tables-config.md; it was not exercised.
- Filters at C+0xbc..0xd8 (current, target, rate, mode per filter) read 1.0 on this path, i.e. the "Filters" smoothing of the record path is off.

4. Strategy update 0x3310d0 collects position changes for A:

The rotation delta is added to **both A and its tracker** (so the eye turns at once), while the rope delta is added to A only (the tracker follows with the lag). Matrix 0x237c48 with angles (0, b, 0): rows (cos b, 0, −sin b), (0, 1, 0), (sin b, 0, cos b), applied as row vector times matrix (0x20b214).
   - zoom: S+8 relaxes towards 1 at 1.0 per second while the target moves, plus K+0x144 (touch zoom, not wired).
5. In 0x2e0bf0 the deltas are applied: A += rope + rotation, tracker += rotation, then the three trackers are advanced with the factors above (A uses one factor for all axes, B and C use the second base).
6. Input accumulators, written by the player controller 0x26be04 each update and cleared by the camera: K+0x13c (DAT_00589bac) += stick x term, K+0x140 (DAT_00589bb0) += shoulders, K+0x144 (DAT_00589bb4) zoom.

### What the camera does against geometry

This is not a sphere or ray sweep. The follow strategy runs 0x3313c0 once per update after the rope, spring and yaw terms (`in+0xe4` = rope and spring delta, `in+0xf0` = yaw delta). K is the camera system 0x589a70, S the strategy 0x58d3e0, `in` the input block (stack, base `auStack_140` of 0x2e0bf0).

1. **Input.** Wanted camera P = A + `in+0xf0` + `in+0xe4` (A = K+4), look point B = K+0x64 (the raw wanted look point, not its tracker). Full distance L = sqrt(D² + H²) with D = `in+0x50`, H = `in+0x54` (quadratic results of 0x330e4c, 10 and 1.7 for OnFoot, so L = 10.1435). The preset block holds the constants: `in+0xcc` 5.0 = reach (block +0x58), `in+0xd0` 2.5 = side gain (+0x5c), `in+0xd4` 1.25 = vertical gain (+0x60). 0x2e10f4 copies them to K+0x1b8, K+0x1bc, K+0x1c0, writes the apex distance R = L + reach to K+0x1c4 (15.1435), copies the surface exclusion mask K+0x170 to K+0x1b0 and the object descriptor words K+0x164 / K+0x168 to K+0x188 / K+0x18c, and calls 0x2d5208 with P and B.
2. **Slab frame (0x2d4ea8 / 0x2eb288).** dir = unit(B - P); right = unit(dir x (0, 1, 0)); up2 = unit(right x dir). Origin O = B - dir * L (the camera position at full distance). Two shapes use the same origin and depth axis: shape A (object K+0x210, "side", horizontal slab) has lateral axis right, plane normal up2 and half width `in+0xd0`; shape B (K+0x1dc0, "up", vertical slab) has lateral axis up2, plane normal right and half width `in+0xd4`. Slab coordinates of a point p: x = (p - O) . lateral, d = (p - O) . normal, y = (p - O) . dir. The pyramid has its apex at y = R (5 units behind B) and half width `size` at y = 0; its side edges are the lines through (0, R) and (±size, 0); K+0x1cc = L - 0.25 is the far limit and K+0x1c8 = min(L - (min(|B - P|, 30) - 0.1), far - 0.01) the near limit (just in front of the camera). The query box is the union of the bounding boxes of the triangles O ± size * lateral, O + R * dir of both shapes.
3. **Gathering (0x2d5208 → 0x20c850 → 0x196990 → callback 0x2d4fd8).** Per collision object (the level master model's items are the objects; placed props are objects of their own, see unknowns), the tree leaves that touch the box are visited depth first, at most 0x100 triangles per object, and a triangle counts when `(1 << surface) & K+0x1b0 == 0`. The camera mask at K+0x170 is **0x01000010** (surfaces 4 and 24 excluded; the first reading 0x10000001 was the byte order of the hex dump). The object descriptor at K+0x184 holds ten words (0xffffffff, 0x30, 0xffffffff, 0, 0, 0x200000, 0x200, 3, self entity pointer, 1) that select objects by layer bits, model flags (0x200 must be set, 3 and 0x200000 must be clear) and exclude the player's own model (0x2d4fd8 also skips a mesh whose model equals the player's). Not decoded which objects of the world pass; the 153 items of the lvl_01 master model are all used here.
4. **Slicing (0x2eb9a0).** A triangle straddles the slab plane when at least one vertex has d > 0 and at least one has d <= 0; the two crossing edges (edge order 01, 12, 20; t = d_b / (d_b - d_a), point = a * t + (1 - t) * b) give a 2D segment (x, y), at most 200 per shape. After each object's batch, if shape A got new segments whose x and y half extents are both below DAT_00379d88 = 1.0 and whose depth centre is more than DAT_00379d8c = 5.0 beyond K+0x1c8, the batch's segments of both shapes are dropped (small objects far from the camera do not count; values read in the oracle, 0x379d88 / 0x379d8c are zero in the file).
5. **Segment pass (0x2eafdc).** Each segment is ordered by x, clipped (0x1eb780: keep the side with n . (p - pt) <= 0, intersect the segment with the line) against the far limit, the left and right side edges and stored as a piece (count byte at +0x111), then clipped against the near limit; the surviving part gives a lateral interval t = x * R / ((R - y) * size) for both ends (ordered low to high here), set to -1 / +1 when an end lies within 0.001 of the near or far limit on the matching side, widened by 0.001 on both sides and stored (at most 50, merged when full). Intervals are sorted by start and merged (0x1eb66c). The widest gap between the merged intervals inside [-1, 1] (first one wins ties, length strictly greater) is stored as (low, high, middle) at K+0x1db4, K+0x1db8, K+0x1dbc for shape A and K+0x3964, K+0x3968, K+0x396c for shape B. Middle = (low + high) / 2, except low = -1 and high < 1 gives high - 1, and low > -1 and high = 1 gives low + 1. No intervals: gap [-1, 1], middle 0; fully covered: gap (0, 0), middle 0.
6. **Re-evaluation (0x2d4e64).** For a candidate camera at distance d from B the near limit is L - (d - 0.1); the stored pieces are clipped against it again and turned into intervals as in 5 (here **without** ordering low and high), giving a new gap for shape A only. 0x2ebe10(scale, shape) returns the largest y of any piece end inside the funnel of half width scale * size.
7. **Clearance S+4 (0x3313c0, flags from the gap of shape A and K+0x140 = shoulder accumulator).**
   - Not turning with L/R: no pull-in when low = -1, or high = 1, or high - low >= 0.5. Turning: no pull-in only when the gap is [-1, 1].
   - No pull-in and S+4 >= 0.99: S+4 = min(1, S+4 + dt / 2) and nothing else moves.
   - Otherwise: not turning: probe = B + unit(P - B) * L; ten times: gap = sweep(|probe - B|), step = step / 2 (first step L), probe += step when high - low >= 0.5, else probe -= step; ratio = horizontal distance(probe, B) / D. Turning: ratio = min(1 - deepest(A, 1) / (L - 0.25), 1 - deepest(B, 1) / (L - 0.25)). The ratio is clamped to [0.01, 1], S+4 = S+4 / 2 + ratio / 2, and the wanted camera is moved onto B + unit(P - B) * S+4 * L (`in+0xe4` += new - P).
   - S+4 scales the next update's distance, height, look height and look depth: `in+0x58 = S+4 * D`, `in+0x5c = S+4 * H`, `in+0x6c` and `in+0x70` times S+4 (0x330e4c). That is how the pull-in persists, and why it recovers by (1 - S+4) / 2 per update while the view stays clear.
8. **Pushes (not turning only, using the gaps of the first sweep).** Side: when |middle| > 0.001 or the gap is (0, 0): `in+0xe4` += K+0x314 (the side axis `right`) * (2.5 * middle); S+0x18 = S+0x1c = 0.5. Vertical: when |middle| > 0.001 or the gap is (0, 0): if the side gap is (0, 0) and the look point moved (`in+0x47`, below) then `in+0xe4` += right * (2.5 * 0.5) and += K+0x1ec4 (up2) * (1.25 * middle * 3), else += up2 * (1.25 * middle); S+0x20 = S+0x24 = 0.5. S+0x24 enters the height spring: factor (0.5 - S+0x24, at least 0) * 0.3 * 2 instead of the constant 0.3, so a vertical push switches the spring off and it comes back linearly over 0.5 s (S+0x24 decays by dt only while `in+0x47` is set; S+0x18, S+0x20 always, S+0x1c with `in+0x47`; 0x330f8c).
9. **`in+0x47`** ("look point moved") is set in 0x2e0bf0 when the squared distance between B (K+0x64) and the previous update's B (K+0x70) exceeds 1e-4 (0x38d1b717); K+0x70 equals K+0x64 after every update. It was the missing piece of "S+0x1c / S+0x24 do not decay while the player stands".
10. **Player push-out.** There is no separate player query. The "player push" of the earlier entry is the vertical push of step 8 (`in+0xd4`); the player only appears as the excluded own model (descriptor word 8). The near limit stops 0.1 in front of the camera and the far limit 0.25 before the look point.

**Command stack (camera object C = 0x08501ad0 in both states, manager 0x376884).**
- C+0x00 is the newest entry, C+0x04 the free list, C+0x0c the capacity (4), C+0x0d the count. Entries are chained through +0x94 (older entry); +0x00..0x38 is the entry's pose (look at +0x00, eye at +0x24, FOV +0x30, +0x34, +0x38), +0x78 the command routine (0 once the entry was merged), +0x80 its argument, +0x84 the fade flag byte, +0x88 the fade time, +0x8c the curve id (u16), +0x9c the weight, +0xa0 the progress, +0xa4 the progress per second, +0xa8 the start time.
- 0x224094 only fills a 0x1c-byte command header {routine, destructor, argument, flag byte +0x0c = 1, time +0x10, curve u16 +0x14 = 5, byte +0x18}. 0x224080 pushes it: when the flag is 0, or 1 with time 0, the whole stack is cleared (instant switch); when the count equals the capacity, 0x2c584c merges the oldest two (below); the entry is built by 0x2a7af0 (progress 0, weight 0, rate = 1 / time, or 10000 for time 0) and its routine is called once.
- Fade times: 0x19b8c8 (record pose) uses the plain mean of the records' BlendTime (+0x30) with curve 5; 0x1b4864 (follow controller) uses 0.5 s (literal 0x3f000000 in the command) with curve 5. Oracle: the PolicePK_03 entry has rate 0.625 (1.6 s), the follow entry rate 2.0.
- Per update 0x2ae250 (called from 0x1cf0b8 inside the manager update): every entry's routine is called with the current player position (old commands keep tracking), then from the newest entry down: progress += dt x rate (clamped at 1; rate 0 gives 1), weight = curve(progress) x remaining, remaining -= weight; the oldest entry gets the remaining weight. If the oldest weight is exactly 0 it is removed. Curve 5 is 0x2b5950 = x x (3 - 2x) (smoothstep). The curves are 12-byte entries at *0x376ad8 (routine pointer at +0, flags at +0xa); entry 4 is 0x1dd648 = 1 - (1 - x)^2.
- 0x2cb5dc sums the entries' stored poses times their weights (look, eye, FOV +0x30, +0x34, +0x38) and divides by the sum of the weights. So the FOV is weighted by the fade too (oracle: 40.0038 one update after the push, 43 at the end).
- **Merge 0x2c584c** (push with 4 entries on the stack): the two oldest entries get their weights normalised to a sum of 1, their stored poses are summed with 0x2cb5dc into the second-oldest entry, which keeps the weight sum, loses its routine (+0x78 = 0, so its pose stays frozen) and stays on the stack; the oldest entry is released. The oracle lobby walk over five records needed this (the fifth push reused the oldest slot 0x08501c6c); without the merge the replica was off by 0.044 after the fifth push.

**Pose filter (0x2a00dc, called at the end of 0x1cf0b8).** The weighted pose goes into C+0x10, the output pose C+0x4c is then `out = out + (new - out) x factor` per update (frame based, not time based): eye (+0x24) and +0x34 / +0x38 use the factor of slot 1 (C+0xcc), look (+0x00) the factor of slot 0 (C+0xbc), the FOV is taken from the sum. The factors are set when a command is pushed: 0x19b8c8 reads the first record's bytes +0x4c (slot 1, eye) and +0x4d (slot 0, look): byte 0 gives 0.3 (0x287a90), otherwise `1 - ease4(byte x 0.02)` = (1 - 0.02 byte)^2 (32 gives 0.1296, 28 gives 0.1936, as read in memory), set at once (rate 1.0, 0x21a538). 0x1b4864 sets both targets to 1.0 with rate 1.0, or 0.1 when the camera is near the follow position (see unknowns); in the oracle both factors read 1.0 in the street and after the hand-over from the record pose.
- Nothing else moves the pose in motion: no spring, no clamp. The record pose is re-evaluated with the new player position every update (0x298cd8) and the filter gives the lag.
