# Script natives: ResetObject (message 8) of the object kinds

Message 8 of ResetObject and EnableSwitch above 0: what kinds 64 and 132 and the default handler write. Split from [script-natives-world.md](script-natives-world.md). For developers; no game assets.

## Current state

- Message 8 (ResetObject, EnableSwitch above 0): the default handler 0x221800 (reached through 0x221760 by other kinds) applies `initialposition` / `initialorientation` and clears the destroyed bit; kind 132 answers it itself the same way (record byte +0xc = 1, returns 1), kind 64 with its own platform reset (0x1a90b8: start position from its record, no destroyed-bit clear, returns 0). Entity +0x44 is the skeleton, so the destroy's 0x2320f8 drops no collision body. 0x237c48 is Rz*Ry*Rx for row vectors. [§2026-10-19T11:06:52](#ts-20261019-110652)

## 2026-10-19T10:42:18+02:00 — ResetObject (message 8) of the default handler 0x221800 for kinds 64 and 132: what it writes and what it leaves (llvm-objdump of artifacts/game/game.arm.elf; no emulator, no REA run)

Corrected by [script-natives-world-reset.md §2026-10-19T11:06:52](#ts-20261019-110652): kinds 64 and 132 answer message 8 themselves, and entity +0x44 is the skeleton, not a collision body.

Continues [script-natives-world.md §2026-10-19T10:02:26](script-natives-world.md#ts-20261019-100226) (kinds 64 and 132, default handler 0x221760). Message 8 is dispatched at 0x221778; 0x221800..0x2218bc is the whole handler and returns 1. Read instruction by instruction, the strings and the constant 0x22191c (0.01745329 = pi / 180) from the image:

- `initialposition` (string at 0x2218f8): 0x241624(entity, "initialposition", 0x2000010, 0) looks the parameter up; when found, the node matrix at entity +0x3c is fetched (0x2429d0), the parameter's float3 is put into a 3-vector (0x2554c0) and the node matrix is set (0x24c118). The translation becomes the parameter.
- `initialorientation` (string at 0x221908): the same lookup; when found, the node matrix is fetched, the three floats are multiplied by 0.0174533 (degrees to radians) and 0x237c48(matrix, x, y, z) rebuilds the rotation, then 0x24c118 sets it. The order of the three rotations inside 0x237c48 was not read.
- Both lookups are tried whether or not the entity is enabled or destroyed; the handler tests nothing first.
- 0x242cf0(entity) enables it: nothing when the halfword +0x10 bit 0 is clear; else it clears bits 0 and 1, walks a table at entity +0x20 calling 0x1cfbbc (not read), shows the node (0x23f734 with 1) and updates (0x242b08, 0x22d5f0, 0x24271c).
- `+0xc &= ~0x10` (0x2218a8..0x2218b0) clears the destroyed bit, and the halfword +4 of the record at +0x7c is set to 0 (0x2218b4).
- Nothing on this path rebuilds the collision body at entity +0x44 that the destroy dropped with 0x2320f8 (that function calls 0x24ce78 and clears +0x58; the pointer +0x44 itself is not cleared). 0x242cf0 touches the component at +0x40 and the pointer +0x84, not +0x44. Whether another system rebuilds the body was not read.
- ResetObject 0x1b25f8 and EnableSwitch with a value above 0 send the message through 0x244fc8; kinds 64 and 132 take this handler, other kinds have their own message 8.

**Port.** `ObjectNativeState::resetDefaultHandler` (`src/runtime/natives_objects.*`) is called by `ScriptRunner::resetEntity` for ResetObject and EnableSwitch above 0: for kinds 64 and 132 it records the object's `initialposition` / `initialorientation` (read from the level object and its class at `loadKinds`) as the restored placement, clears the destroyed bit and the disabled bit. `PlacedObjectState::collisionDropped` is set by every destroy and not cleared by the reset, so `isDisabled` (the collision tests) still skips the entity; a reset entity is destroyed again by the next DestroyProp. Pinned by `natives-objects` (synthetic) and `natives-objects-real-data` (lvl_04 `4-1_Crate_Faller_Platform`, kind 64: position (1359.36, 48.4659, -1081.43), orientation (0, 0, 0), printed by the C++ loader on 2026-10-19; equal to its placement). Nothing in the port moves a kind 64 object yet, so the restored placement is a record.

**Unknowns.** The rotation order of 0x237c48; the meaning of the record halfword +4 (the port has no reader); whether the collision body is rebuilt by another system after a reset; the message 8 of kinds with their own handler.

## 2026-10-19T11:06:52+02:00 — Message 8 again: kinds 64 and 132 answer it themselves, entity +0x44 is the skeleton and no collision body, the rotation order of 0x237c48 (llvm-objdump of artifacts/game/game.arm.elf with --mcpu=arm1176jzf-s --mattr=+vfp2; no emulator, no REA run)

[Corrects §2026-10-19T10:42:18](#ts-20261019-104218): kinds 64 and 132 do not run the default handler 0x221800 for message 8, and 0x2320f8 drops no collision body. [Corrects script-natives-world.md §2026-10-19T08:53:30](script-natives-world.md#ts-20261019-085330) where it calls 0x2320f8 the collision body drop.

- **Entity +0x44 is the skeleton / animation set, not a collision body.** [objects.md](objects.md) (0x2442b4) loads the `.fnskl` into +0x40 / +0x44. 0x2320f8(entity) hands `[entity+0x44]` to 0x24ce78 (a loop over the byte +2 & 31 track entries of 88 bytes at pointer +0x2c, each stopped by 0x24cf70 and released through a per-type table) and clears `[entity+0x58]`; the pointer itself stays. The entity constructor (0x232478) zeroes +0x44 and +0x58, and the stores to +0x44 elsewhere (0x240de4, 0x22de44, 0x23c100, 0x2584b4) belong to other structures. Nothing in the entity grid is touched: the grid keeps its entries ([collision.md](collision.md) §2026-10-13T20:43 and its consequence), the player layer tests only the owner's halfword +0x10 (bits 0 and 1 excluded, 0x200 required) and no layer tests bit 0x10 of +0xc. So there is no collision body to rebuild, and the port's `collisionDropped` (SCRIPT-S258) has no original behind it. What a destroy does to the skeleton (the animation tracks are stopped) is real but is an animation effect.
- **Kind 64 (0x1a8d74) handles message 8 itself, at 0x1a90b8.** It is not the default handler: with the platform record R at entity +0x7c, `R+4` (halfword) is set to 2 when the byte `R+0xb4` is 0 and to 0 for 1 to 6 (unchanged above); the node matrix is fetched (0x250810); when the halfword `R+0xb6` has bits 0xc00 the rotation comes from 0x248870 on `R+0x30`, otherwise, when `R+0x50` and its word +8 are non-zero and the parameter `initialorientation` (flags 0x2000010) exists, the rotation is rebuilt from it (degrees times 0.0174533, 0x237c48); the translation is set from `R+0x18` (the platform's own start position, **not** the `initialposition` parameter), the float at `R+0x7c` is set to a constant (0x1a906c), the node matrix is set (0x24c118), the entity is enabled (0x242cf0), and when `(R+0xc) & 31` is 1 or 2 the attachment routine 0x23211c(entity, R+0xc, 0) runs. It returns 0 (0x1a8e20) and does **not** clear bit 0x10 of +0xc. Every other message goes to 0x221760.
- **Kind 132 (handler 0x1ba1dc) handles message 8 itself, at 0x1ba268.** It sets the byte `R+0xc` to 1, enables (0x242cf0), applies `initialposition` as the translation and `initialorientation` as the rotation exactly like 0x221800, clears bit 0x10 of +0xc and returns 1. It does not write the halfword `R+4`. Messages 251, 252 and 255 are its own; the others tail into 0x221760.
- **The default handler 0x221800 is reached by** other kinds that tail into 0x221760: the handlers at 0x18c100 (kind 102, which sends unhandled messages there; whether it answers 8 first was not read) and 0x1d8b88 (kind not identified). The record halfword +4 that 0x221800 clears has no reader in 0x221760; its readers in the kind 64 record are not read.
- **0x237c48 order.** With sin / cos of x, y, z (0x249038: r0 = sin, r1 = cos) it writes the three rows (stride 16 bytes) `[cy cz, sx sy cz + cx sz, sx sz - cx sy cz]`, `[-cy sz, cx cz - sx sy sz, sx cz + cx sy sz]`, `[sy, -sx cy, cx cy]`, the transpose of Rx(x) Ry(y) Rz(z) for column vectors, i.e. the rotation Rz * Ry * Rx for row vectors (x applied first). This is the same result as [levels.md](levels.md) (disassembly of the same function, 2026-10-12); read again here with the VFP instructions decoded.

**Unknowns.** Whether the skeleton's animation is rebuilt after a reset (0x242cf0 walks a table at +0x20 calling 0x1cfbbc, not read); why the kind 64 reset leaves bit 0x10 of +0xc set; the readers of the kind 64 record fields `R+4`, `R+0xb4`, `R+0x7c`; what kind 0x1d8b88 is and which other kinds answer message 8 themselves (the census of all 173 handlers was not done).
